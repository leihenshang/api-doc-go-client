> 审核日期：2026-10-26  
> 审核对象：`api-doc-go-client`  
> 代码基线：`master @ 428ab0652e443ea5dc799d015d2fbd240a17b39b`  
> 审核方式：静态代码审查、关键调用链核对、工程门禁、非缓存 Go 测试、完整 Playwright e2e。

## 1. 结论摘要

客户端的主架构已经比较完整：本地 YAML 文件是真相源，Go 内核负责集合、执行、同步与 MCP，Vue 前端负责多页签会话；原子写、磁盘哈希冲突检测、PAT 密文存储、请求重定向凭据保护和 devserver 门禁均已有实质实现。

当前主要风险不在“缺少大块功能”，而在**异步状态推进和失败路径的一致性**：

1. **P0：文档自动保存会把保存期间的新编辑误标为已保存，存在静默丢失风险。**
2. **P1：请求自动保存在慢写盘期间可能失去后续保存调度。**
3. **P1：远端变量/环境删除在本地落盘失败时仍清同步摘要，残留数据下一轮可能被重新推回服务端。**
4. **P1：取消一个未落盘草稿会取消同集合的全部草稿发送。**
5. **P1：完整 e2e 当前不是全绿，104 条执行结果为 100 通过、4 失败；发布前必须逐条归因。**
6. **P2：功能现状文档存在多处漂移，已经把未通过的完整门禁写成“恢复全绿”。**

建议下一阶段先做**数据一致性修复、故障注入回归和发布验收**，再进入 Git 多同步源等扩展功能。现有静态门禁和单元测试全部通过，并不能覆盖上述慢 I/O、保存中编辑、本地删除失败等时序边界。

### 优先级口径

- **P0**：可能静默丢失用户编辑，应在任何新功能前处理。
- **P1**：明确影响同步、自动保存、执行控制或发布可信度，应紧随 P0 处理。
- **P2**：文档、兼容性和可选增强，可在核心稳定性恢复后安排。

## 3. 已确认问题

### C-01（P0）文档自动保存会误清后续编辑的脏标记

**证据**

- `frontend/src/stores/tabs.ts:247-269`：`saveDoc` 直接把当前 `tab.doc` 交给异步 IPC，成功后无条件执行 `tab.dirty = false`，没有保存快照或编辑代次比较。
- `frontend/src/stores/tabs.ts:280-290`：`touchDoc` 只在 `!tab.dirty` 时安排一次定时器；连续编辑不重置防抖，保存期间的新编辑也不会安排第二次保存。
- `frontend/src/composables/useCloseFlow.ts:89-102`：干净页签直接关闭，只有脏页签才出现未保存保护。

**触发序列**

1. 开启自动保存，编辑文档得到版本 A，800ms 定时保存开始。
2. IPC 写盘尚未返回时继续输入，内存变为版本 B。
3. 本次实际落盘的仍是 A，但保存返回后 `dirty` 被无条件清为 `false`。
4. B 没有新的保存定时器；此时关闭页签会被视为干净页签，不再询问，B 可只存在于随即销毁的内存中。

**影响**：静默丢失文档编辑，且关闭流程无法兜底。这是本次审核优先级最高的问题。

**最小修复方向**

- 每个文档页签维护单调递增的编辑代次；保存开始时同时快照内容与代次。
- 保存成功后，仅当代次未变化才清脏；若期间又编辑，必须保留脏标记并安排一次尾次保存。
- 文档编辑按“最后一次输入后防抖”重置定时器，保存过程保持 single-flight，避免并发写同一文件。

**验收测试**

用可控延迟的保存 Promise 覆盖“第一次保存未返回时再次编辑”：第一次完成后不得清脏，必须发生第二次保存，最终磁盘包含全部编辑；保存中关闭仍应出现未保存提示。另覆盖保存失败不产生自动重试风暴。

### C-02（P1）请求自动保存缺少尾次调度

**证据**

- `frontend/src/stores/tabs.ts:509-514`：编辑后安排 800ms 防抖保存。
- `frontend/src/stores/tabs.ts:519-560`：`flush` 遇到 `tab.saving` 直接返回；请求保存已经通过快照和 `editedAgain` 避免误清脏，但成功后没有为 `editedAgain=true` 再安排保存。
- `frontend/src/stores/tabs.ts:581-584`：`finally` 只恢复保存状态，不检查是否有保存期间的后续编辑。

**触发序列**

第一次保存超过 800ms 时，后续编辑产生的定时器会在保存期间触发并因 `tab.saving` 返回。原保存完成后虽然正确保留了脏标记，但定时器已经消费，之后不再编辑就一直不会自动保存。

**影响**：不会立即误清脏，关闭时仍有提示，但“自动保存”会悄悄退化成需要再次编辑或手动保存；异常退出时最新内容仍可能未落盘。

**修复与验收**

与文档共用明确的保存状态机：single-flight + 编辑代次 + trailing save。仅在“本次保存成功且保存期间确有新编辑”时续调，失败时保持脏标记但不要形成紧密重试循环。测试需模拟写盘超过一个防抖周期，并验证停止输入后最终自动落盘。

### C-03（P1）变量/环境删除失败仍推进同步基线

**证据**

- `internal/syncengine/engine.go:884-927`：example/doc/field_mapping 已做到“本地删除成功才清摘要并上报错误”，variable 和 variable_env 却无条件走清理路径。
- `internal/syncengine/engine.go:915-919`：变量删除后无条件 `delete(e.Bind.VarHashes, it.UID)`。
- `internal/syncengine/engine.go:931-946`：`removeVarByUID` 不返回错误，且 `_ = e.Coll.SaveEnv(env)` 静默吞错。
- `internal/syncengine/engine.go:964-979`：环境删除吞掉 `DeleteEnv` 错误，仍清理自身及相关变量摘要。
- `internal/syncengine/engine.go:1469-1557`：`collectVarOps` 以摘要是否存在判断新增/变更；本地残留条目若已无摘要，会被生成 upsert。
- `internal/collection/collection.go:1424-1475`、`1520-1535`：`SaveEnvChecked` 与 `DeleteEnv` 都会返回真实文件错误，错误是在 syncengine 层被丢弃的。

**后果**

当权限、磁盘或其他文件错误导致本地删除未生效时：

1. 本轮 `Report.Errors` 看不到删除失败；
2. 同步摘要却被清除；
3. 下一轮扫描仍能看到本地残留条目，并将其当作新增/变更重新 upsert；
4. 用户可能看到“远端删了又回来”，同时没有明确错误解释。

**最小修复方向**

- 让 `removeVarByUID` / `removeEnvByUID` 返回错误并接入 `applyDelete.fail`。
- 仅在本地删除成功，或确认目标已不存在（幂等成功）后清理摘要；失败时保留摘要供后续重试。
- 明确环境主文件和 secrets 文件只移动成功一部分时的恢复语义，保证重试可收敛。
- 不要以“避免重复推送删除”为理由清除一个实际尚未完成的本地删除基线。

**验收测试**

通过文件操作故障注入分别让 `SaveEnv`、`DeleteEnv` 失败，断言：错误进入报告、摘要保持、下一轮不会 upsert 残留条目、故障解除后能够重试删除。现有测试检索未见这类故障路径覆盖。

### C-04（P1）同集合草稿的取消操作粒度过粗

**证据**

- `frontend/src/stores/tabs.ts:300-307` 已为草稿页签生成独立临时 `tab.uid`，但 `frontend/src/stores/tabs.ts:729-761` 实际发送和取消仍使用 `tab.request.uid`；未落盘草稿该值为空串。
- `internal/app/app_misc.go:336-343` 的登记语义是空 uid 草稿“单独登记（互不取消）”。
- `internal/app/app_misc.go:381-410` 却在 `CancelSend("")` 时选择活动根下的全部草稿并逐一取消。
- `internal/app/multicoll_test.go:207-250` 只验证不同集合各一个草稿的隔离，没有覆盖同一集合两个并发草稿。

**触发序列**：同一集合新建两个未落盘草稿并同时发送，在其中一个页签点击取消，另一个也会被取消。

**修复与验收**

将“集合实体 uid”和“一次发送的取消标识”解耦，发送与取消使用同一个独立 send ID；不要把空 uid 同时当作一类请求的标识。至少补充：同集合两个草稿只取消目标、跨集合互不影响、同一页签重发只取消自己的上一轮、已落盘请求行为不变。

- 前端 `src` 未见 store 级单元测试，保存回归主要依赖 Playwright；现有用例没有可控的慢保存 Promise，难以稳定覆盖 C-01/C-02。

## 7. 下一阶段开发方向

### P0：先恢复数据正确性与发布可信度

1. **统一请求/文档保存状态机**  
   用户价值：连续输入、慢盘、异常退出时仍不丢编辑。  
   前置依赖：可控延迟或故障的保存测试替身。  
   验收：C-01/C-02 的保存中编辑用例稳定通过，冲突和只读行为不回归，失败后无重试风暴。

2. **修复同步删除的失败事务边界**  
   用户价值：本地故障可解释、可重试，不会把已删除数据静默复活。  
   验收：变量、环境、文档、示例、字段字典遵循同一“成功才推进基线”规则；fault-injection 用例覆盖部分失败和恢复。

3. **归因并恢复完整 e2e，再补发布验收**  
   用户价值：发布结果可复现，避免只在开发机 Chromium 环境可信。  
   验收：104 条全量用例通过；`@smoke` 进入自动门禁；Linux/WebKitGTK 与 Windows/WebView2 完成真实窗口核对；deb 安装、启动、升级、卸载以及 prod/dev 共存有记录；明确签名和发布流程。

### P1：完成高价值的协作与检索能力

1. **Git 多同步源最小垂直闭环**  
   用户价值：集合可直接进入既有 Git 评审、版本和离线工作流。  
   前置依赖：先更新《多同步源支持可行性与设计方案-评审》的行号与语义基线，修正 rebase ours/theirs、abort 顺序、pull 后基线对齐等旧问题，不能直接照当前旧方案实现。  
   建议首刀限定单分支和明确的工作树根边界，不做 YAML 语义合并，不改动现有服务端同步协议。  
   验收：干净同步、本地提交、远端推进、冲突副本与中止恢复全链路通过；pull 后不会全库 dirty；`.sync.json`、secrets、`.trash`、`.conflicts` 不会被暂存；Git 命令禁交互且有超时。

2. **文档正文纳入本地搜索**  
   用户价值：现有请求 URL/方法搜索之外，能直接定位 Markdown 说明中的业务知识。  
   前置依赖：文档索引、外部文件变更和索引重建使用同一失效机制。  
   验收：正文命中可打开对应文档页签，外部修改可更新，集合切换不串结果，大文档有明确大小/结果上限。

3. **修复草稿发送身份模型**  
   可与执行器体验一起收口，不必等待大型新功能。验收以 C-04 的并发矩阵为准。

### P2：按真实需求选择增强，不建议同时铺开

| 方向 | 用户价值 | 关键前置与验收 |
|---|---|---|
| 集合运行器数据驱动 | 用 CSV/JSON 数据集重复执行同一请求树，提高 CI 覆盖 | 定义行级变量作用域、失败隔离和报告聚合；JUnit 保留每条数据行结果，敏感值不进报告 |
