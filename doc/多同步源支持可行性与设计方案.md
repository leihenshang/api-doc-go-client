# 多同步源支持：可行性与设计方案

> 分析对象：`api-doc-go-client`（Wails v2 + Go 内核 + Vue3）
> 代码基线：`internal/syncengine`、`internal/collection`、`internal/app/app_sync.go`、`frontend/src/components/SyncDialog.vue`
> 日期：2026-10-19
> 结论依据：全部来自当前仓库代码实读（含行号索引，见附录 A），不含推测性描述。

---

## 0. 结论摘要

**问题**：能否在现有服务端同步（自建 api-doc-go）之外，再接一个 Git 同步源？

**结论**：**技术可行，但两者不是同一层的东西，不能"换一个实现"了事。**

| 判断 | 结论 | 依据 |
|---|---|---|
| 能不能接 Git | ✅ 可行，且改动面比预期小 | 集合本身就是纯文本文件（`opencollection.yml` + `*.yml` + `docs/*.md`），文件即真相源；已有 fsnotify 监听 + 索引重建 + 冲突 UI 可复用 |
| 能不能复用现有 `syncengine` | ⚠️ 只能复用一半 | `pull→apply` 的**语义层**绑死了服务端协议（`cursor`/`base_rev`/`op_id`/六类实体），Git 提供不了；**文件落地、状态栏、冲突展示、定时器**可复用 |
| 能不能双源同时写同一集合 | ❌ 不能 | 两套冲突模型（LWW+副本 / 三方合并）会互相覆盖，必须"同一集合同一时刻只有一个写通道" |
| 难度 | 中（约 19–31 人日，不含 LFS/子模块等边缘；详见 §6） | 难点不在 git 命令，在冲突映射、跨平台错误处理、双模状态模型 |
| 推荐 | **Git 作"版本层/个人协作层"，服务端作"团队协作层"，二选一绑定，不做双写** | 见 §8 |

三条关键判断展开：

1. **服务端同步是"记录级增量"，Git 是"文件级快照"。** 前者有实体语义（uid、六类实体、字段级 extra、权限位），后者只有 blob/tree/commit。把 Git 塞进 `Client` 接口会得到一个"最小公倍数"接口，反而丢掉服务端已有的 `cursor`/`base_rev` 能力。
2. **Git 的收益恰好补上现有同步的最大短板：无损。** 现协议对 gRPC 只同步说明（`syncrows.go:53-56`）、`field_mapping` 不同步、附件只镜像同源图片（`app_doc.go:146-163`）。Git 同步的是文件字节，这些全部保真。这是 Git 方案最硬的价值点。
3. **Git 的代价恰好是现有方案的强项：冲突粒度与权限。** Git 冲突是整文件级、YAML 冲突标记会直接破坏解析（`share/collection` 的 `yaml.Unmarshal` 失败）；也没有 `PermUpdate`/`PermDelete` 这种字段级权限和 `device` 溯源。

## 1. 现状盘点：已有的同步逻辑到底做了什么

### 1.1 分层与文件地图

| 层 | 位置 | 职责 | 规模 |
|---|---|---|---|
| App 门面 | `internal/app/app_sync.go` | 绑定/解绑、令牌解析、定时器、状态聚合、冲突门面 | 418 行 |
| 同步引擎 | `internal/syncengine/engine.go` | 一轮同步编排：协商→拉取→应用→推送→回执 | 1219 行 |
| 协议客户端 | `internal/syncengine/client.go` | 5 个 HTTP 端点 + URL 校验 + 统一响应解包 | 256 行 |
| 协议 DTO | 共享库 `share/syncapi` | 客户端/服务端同一份结构体别名，编译期对齐 | — |
| 文件层 | `internal/collection` | 集合扫描、请求/文档/示例/环境读写、索引、冲突副本 | ~11800 行（含测试） |

| UI | `SyncDialog.vue` + 状态栏 | 绑定表单、口令、冲突三选一 | 412 行 |

### 1.2 一轮同步的确定性流程

```
RunOne (engine.go:179)
 ├─ negotiate()            GET  /api/meta          → 校验 sync_proto≥1 且 features 含 sync/change_log
 ├─ pull()                 GET  /api/sync/state     → 服务端 cursor
 │   ├─ 本地 cursor=0      → snapshot(offset,500)   全量，≤200 页
 │   ├─ 服务端 cursor>本地 → changes(since,500)    增量，≤200 页；gap=true 降级 snapshot
 │   └─ 相等              → 跳过拉取
 │   applyItems()  按 typeRank 排序：group→api→doc→example→variable_env→variable
 ├─ pushDirty()            POST /api/sync/push     精确 dirty + tombstone
 │   回执 ok → MarkSynced(uid, hash, item_rev)；conflict → .conflicts/；rejected → 计入 Report
 └─ rep.Cursor = bind.Cursor
```

关键细节（都影响 Git 方案的设计）：

- **拉取应用以"服务端版本覆盖本地"为准**：`api` 本地 dirty 时先存字段级副本（`saveLocalIfDirty` at `engine.go:401`）；`doc/example/env` 于 2026-10-19 起在覆盖前存**整文件快照**（`snapshotDocIfDirty` 等），同样进 `.conflicts/`。
- **推送是一批 ops，服务端按 `op_id` 幂等**；冲突判定用 `base_rev != last_change_id`。
- **游标只会前进**，`has_more` 或游标不前进都会停止（`engine.go:238-254`）。
- **能力协商失败即整轮失败**（`engine.go:265-279`），不会带旧协议硬跑。

### 1.3 本地同步状态存在三个地方

| 载体 | 内容 | 是否进 git | 用途 |
|---|---|---|---|
| `.sync.json`（0600） | `linked/serverUrl/projectId/mode/cursor/token` + `docHashes/exampleHashes/envHashes/varHashes` | 已加入 `.gitignore`（`collection.go:68-69`） | 绑定信息 + 非索引类实体的脏检测基线 |
| 本地 SQLite 索引（配置目录） | 每个节点 `hash`（当前）、`syncedHash`（上次同步）、`baseRev` | 否（`collection.go:224-239`） | 接口/分组的精确 dirty 集 + 冲突基线 |
| `.conflicts/` | 接口：`*.conflict-<ts>.yml`（去 uid，附 `conflict_of/server_rev/server_payload`）；文档/示例/环境：`<kind>-<name>-<ts>.yml`（整文件快照） | 已忽略 | 冲突留底 + 三选一 / 整份还原的数据源 |

`.trash/` 存删除（可恢复），同样被忽略。

### 1.4 现状的 7 条隐含假设（这是"能不能接第二个源"的真正约束）

| # | 假设 | 代码位置 | 对 Git 的影响 |
|---|---|---|---|
| 1 | 远端有**项目级单调游标**，能表达"自某点以来的变更" | `engine.go:203-256` | Git 没有游标，只有 commit sha 与 tree diff；需换一套"变更检测" |
| 2 | 每个条目有**稳定 uid**，改名/移动不丢身份 | `index.Node.UID`、`folder.yml/meta.uid` | Git 以路径为身份；本地现状"改名不改文件名"（`RenameRequest:1596`）反而降低冲突面，但移动会变成 rename + 内容改动 |
| 3 | 每个条目有**服务端版本号 base_rev** 做冲突基线 | `index.Node.BaseRev` | Git 用 merge-base 做基线，语义更强（三方）但粒度是文件 |
| 4 | 删除通过**墓碑**传播 | `LoadPendingDeletes`/`ClearPendingDeletes`（`engine.go:812,851`） | Git 删除就是文件删除，天然传播；但"离线删 vs 远端改"是 modify/delete 冲突 |
| 5 | 实体只有 6 类，字段是有损子集 | `typeRank`（`engine.go:329-346`） | Git 同步的是字节，无损；也意味着 Git 模式下"服务端能表达的"不再是上限 |
| 6 | secret 值可加密出网，也可选择不出去 | `collectVarOps`（`engine.go:1018-1107`） | Git 直接靠 `.gitignore` 排除 `environments/*.secrets.yml`，压根不出去 |
| 7 | 绑定的"一个集合一个服务端项目" | `BindInfo`（`client.go:28-49`） | Git 需要 `remote + branch`，是**同一抽象位的另一个取值**，不是并存 |

> 结论：假设 1/3/4 是 Git 无法满足的，假设 2/5/6/7 是可以对齐或天然更好的。所以 Git 接入的正确姿势是**新增一个 provider 实现**，而不是改造 `Engine` 去兼容两套协议。

## 2. 两种同步模式在实现机制上的真实差异

### 2.1 一句话本质

- **服务端模式**：客户端把"一次改动"翻译成业务事件（`upsert api uid=X payload=...`），服务端维护流水账，客户端按游标消费流水账。**同步的单位是"条目 + 字段"**。
- **Git 模式**：客户端把"一组文件变化"提交成 commit，远端维护 commit DAG，客户端按 merge-base 做三方合并。**同步的单位是"文件 + 行"**。

这决定了后面所有差异：粒度、冲突、删除、身份、权限、审计。

### 2.2 逐维对照

| 维度 | 服务端（现状） | Git | 差异性质 |
|---|---|---|---|
| 真相源 | 本地文件；服务端另存一份结构化副本 | 本地文件；远端存 blob 树 | 相同（都是文件优先） |
| 变更检测 | 内容 sha256 + `syncedHash`（索引）或 `*.Hashes`（`.sync.json`） | `git status` / tree diff（按 blob oid） | Git 更彻底：连"改动是否已提交"都能区分 |
| 增量单位 | change_log 记录（一条 = 一个条目的一次变更） | commit / blob diff | 服务端更细（字段级），Git 更粗（文件级） |
| 冲突基线 | `base_rev`（单值，LWW） | `merge-base`（三方） | Git 理论更强，但只对文本行有效 |
| 冲突表现 | 服务端返回 `conflict` + 服务端版本；本地版本进 `.conflicts/`，UI 字段级三选一 | 工作区写入 `<<<<<<<` 标记；或直接 abort 由 UI 整文件取舍 | **体验差异最大的一处** |
| 冲突粒度 | 字段（name/method/url/docs） | 文件（整份 YAML） | Git 粗，但对 `*.yml` 单文件单条目场景其实够用 |
| 删除 | tombstone（uid 列表 persist 到 `.sync.json`） | 文件删除进入 diff | 等价，Git 更自然 |
| 重命名 | 只改 `info.name`，**文件名不动**（`RenameRequest:1596`） | 路径变化（git 通常识别为 rename） | 现状实现让 Git 更好过：改名不产生路径冲突 |
| 移动分组 | `os.Rename` 文件 + 改 `Path`（`MoveRequest:1613`） | 同上，目录级 rename | 基本相同 |
| 身份 | `meta.uid`（uuid v4），服务端 `ext_uid` | 无（路径即身份） | Git 模式下 uid 退化为"给 UI/索引用的本地键" |
| 字段保真 | 有损：21 个字段 + 6 类实体；gRPC 仅说明；`field_mapping` 不同步 | 无损：整个文件字节 | **Git 的核心优势** |
| 二进制/附件 | 仅 best-effort 镜像同源图片到 `assets/`（`app_doc.go:146`） | 需 LFS 或直接入库 | 都不完美；Git + LFS 需额外处理 |
| 鉴权 | PAT/JWT，`AuthOrPAT`，字段级权限位 | 仓库级 read/write | 服务端细，Git 粗 |
| 审计 | `change_log` 的 `device/actor`，Web 可查 | commit author + 历史 | Git 更通用（blame/PR），但没有权限审计 |
| 实时性 | 轮询：默认 120s，仅活动根（`StartAutoSync:302`） | 无推送；需 `fetch` 才发现远端变化 | 服务端可控，Git 更被动 |
| 离线 | 可编辑，dirty 累积，联网补推 | 可编辑 + 本地 commit，联网 push | Git 离线体验更好（有历史） |
| 首次接入 | URL + projectId + PAT，**projectId 需手填**（`SyncDialog.vue:218-224`） | clone URL + 凭证（SSH/credential helper） | Git 更符合开发者习惯 |
| 依赖 | 一个 HTTP 服务 | 需要 git 可执行文件 | Git 有环境门槛 |
| 仓库/存储成本 | 服务端库（指针 + 结构化副本） | 每版本全量 blob（含二进制） | Git 随历史线性膨胀 |

### 2.3 五个最容易踩的具体差异

**(1) 身份：uid 还是路径**

现有 `uid` 的价值在"离线改名/移动后服务端仍认得出是同一条"。Git 用路径，路径一变就是 delete+add。但现状 `RenameRequest` **刻意不改文件名**，`MoveRequest` **只移动目录/文件**——这意味着 Git 视角下：
- 改名 = 文件内容一行变化（`info.name`），git 能正常 diff；
- 移动 = rename（git 相似度识别），历史可跟随；
- 只有"改名 + 同时移动"才会退化成 delete+add。

这是个**意外的兼容红利**：现有文件命名策略恰好让 Git 的路径身份够用。

**(2) 冲突：字段级 vs 整文件**

服务端的冲突是"服务端版本落回本地 + 本地版本进 `.conflicts/` + UI 展示 4 个字段的 diff"（`export.go:94-108`）。

Git 的冲突是把 `<<<<<<<` 写进工作区文件。对 `*.yml` 来说这是**破坏性的**：`share/collection.DecodeRequest` 会解析失败，扫描器读不出这个条目，侧栏里可能直接"消失"或报错。

因此 Git 模式**不能采用"让冲突标记留在工作区"的策略**，必须：
- 要么 `merge --abort` 后由 UI 做整文件二选一（推荐，与现有交互同构）；
- 要么用 `git show :2:path` / `:3:path` 取 ours/theirs 两份内容，落成 `.conflicts/` 副本再 abort。

绝不能做"YAML 语义级三方合并"——那等于重写一套结构化 diff/merge，工作量远超本次目标，也与现有"不做字段级三方合并"的既定边界冲突。

**(3) 删除：墓碑 vs 文件消失**

服务端要靠 `pendingDeletes` 记住"我删过 uid=X"，否则下一轮 pull 会把它复活（`engine.go:812,833,851`）。

Git 不需要墓碑：文件没了，commit 里就是 delete。但会出现经典 **modify/delete 冲突**：A 删了接口，B 改了接口。Git 会拒绝 merge；服务端则会一条一条判定（删除与 upsert 分别走 `applyDelete`/`applyUpsert`，谁后到谁赢）。

**(4) 保真：有损 vs 无损**

| 内容 | 服务端同步 | Git 同步 |
|---|---|---|
| HTTP 21 个字段 | ✅ | ✅ |
| gRPC 的 proto/target/message/TLS | ❌ 只同步 `docs` | ✅ |
| `settings` / `script` / `asserts` | ✅（作为 extra JSON） | ✅ |
| `field_mapping` | ❌ 服务端独有，客户端无模型 | ✅（若在文件里） |
| `assets/` 图片 | ⚠️ 仅同源图片镜像 | ✅（需 LFS 或直接提交） |
| `environments/*.secrets.yml` | ✅ 口令加密后出网 | ❌ 被 gitignore 排除 |
| 未知顶层字段（Bruno 兼容） | ❌ 服务端不存 | ✅ 原样保留 |

**(5) 凭证与 secret**

- 服务端：PAT 存 `.sync.json`（0600，已 gitignore），UI 回显（`SyncDialog.vue:84-85`）；secret 变量需设口令才出网，未设则跳过（`engine.go:1074-1085`）。
- Git：凭证交给系统（credential helper / SSH agent / `GIT_ASKPASS`），客户端不该自己存；secret 文件被忽略，**团队必须另建分发渠道**（这是安全优势，也是协作成本）。

## 3. Git 作为同步源的方案设计

### 3.1 三种落法

| 方案 | 机制 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **A. 调系统 git CLI** | `exec.Command("git", ...)`，解析 `--porcelain=v2 -z` | 零新依赖；与用户手敲行为完全一致（hooks、credential helper、LFS filter、`core.autocrlf` 全兼容）；出问题可直接让用户命令行复现 | 依赖 git 存在；要处理 Windows 路径/编码、退出码、`stderr` 翻译；不能用 `-z` 之外的格式（易变） | ✅ **推荐** |
| **B. 内嵌 go-git** | 纯 Go 实现 fetch/merge/push | 无外部依赖，跨平台一致；可做"只读 fetch"轻量场景 | LFS 支持弱；SSH 配置/credential helper 兼容差；`autocrlf/filemode/submodule/shallow` 行为与原生不一致；引入大依赖树 | ⚠️ 仅在"必须免 git 依赖"时考虑 |
| **C. 混合** | 默认 CLI，未装 git 时降级只读或提示 | 兼顾 | 两套代码路径，测试翻倍 | 不建议首版 |

选 A 的核心理由：目标用户是 API 开发者，git 普及率高；而 B 的"隐藏不一致"会制造最难排查的支持问题——"命令行能 push，客户端不行"。

### 3.2 模块划分

```
internal/gitsync/
  provider.go    Provider 接口 + 能力声明
  runner.go      exec git 封装（超时/环境/退出码/stderr 截断）
  status.go      git status --porcelain=v2 -z → 变更集
  sync.go        fetch / pull --ff-only / rebase / commit / push 编排
  conflict.go    merge 冲突 → abort → ours/theirs 落 .conflicts/
  errors.go      git 错误 → 中文可操作提示（"未配置 user.email" 等）
```

`Provider` 接口刻意**不做成 `syncengine.Client` 的同构物**：

```go
type Provider interface {
    Kind() string                                             // "git"
    Status(ctx) (Status, error)                               // ahead/behind/dirty/conflicts
    Pull(ctx) (PullResult, error)                             // fetch + ff-only/ rebase，失败即 abort
    Push(ctx, msg string) (PushResult, error)                 // add 白名单 + commit + push
    Conflicts(ctx) ([]Conflict, error)                        // 复用 collection.ConflictItem 形状
    Resolve(ctx, id, choice string) error                     // local | remote
}
```

App 门面按 `BindInfo.Kind` 分派：`server` → `syncengine.Engine`；`git` → `gitsync.Provider`。`SyncStatus`/`SyncReport` 保持同一前端契约，只增加 `kind/ahead/behind` 字段。

### 3.3 关键流程

**首次接入**

1. 用户在集合目录执行 `git init` 或 `git clone <url> <dir>`（客户端只检测 `.git` 是否存在，不主动 clone 到用户已有目录）；
2. 绑定面板填 remote（默认 `origin`）+ branch（默认当前分支）；
3. 客户端校验：`git rev-parse --is-inside-work-tree`、`git config user.email`（缺则提示，不自动写全局配置）、远端可达（`git ls-remote --exit-code`）；
4. 写 `.sync.json`：`kind:"git", remote, branch, lastCommit`。

**一轮同步**

```
Pull:
  git fetch --prune origin <branch>
  behind = rev-list --count HEAD..origin/<branch>
  if behind == 0 → 结束
  if dirty == 0 → git merge --ff-only origin/<branch>
  else        → 先 Commit（本地改动成 commit），再 git rebase origin/<branch>
                 rebase 冲突 → git rebase --abort → 冲突副本 → 报错给 UI（不自动解决）

Push:
  git status --porcelain=v2 -z → 过滤白名单路径
  git add -- <白名单>
  git commit -m "sync(<device>): <n> changes"
  git push origin <branch>
```

**冲突**

- 统一 `abort` 到同步前状态（`merge --abort` / `rebase --abort` / `cherry-pick --abort`），保证工作区永远可解析；
- 用 `git show :2:<path>`（ours）与 `:3:<path>`（theirs）导出两份到 `.conflicts/<name>.conflict-<ts>/`；
- UI 复用现有冲突面板，`mode` 从 `fields` 改成 `file`（整份 YAML 对照），选择后写回并重新 commit。

**删除**

不做墓碑。本地删除即文件删除，随 commit 传播。modify/delete 冲突由上面的 abort + 二选一兜底。

### 3.4 复用与新增

| 能力 | 现状 | Git 模式 |
|---|---|---|
| 文件监听 → 索引重建 → 前端刷新 | ✅ `watchLoop`（`app.go:445-483`），已忽略 `.git` | **直接复用**，git pull 落地即自动刷新 |
| 脏计数 | `DirtyNodesFast` + `Hashes` | 换成 `git status`，口径映射到同一字段 |
| 定时同步 | `StartAutoSync`（120s，仅活动根） | 复用同一调度器，把 `runSyncFor` 换成分派 |
| 状态栏 | `GetSyncStatus` + 2s TTL 缓存 | 复用，新增 ahead/behind |
| 冲突 UI | `ConflictResolver.vue` 字段级 | 新增文件级模式（或并列组件） |
| 绑定 UI | `SyncDialog.vue` 服务端表单 | 增加"同步源"选择 + Git 面板 |
| secret 加密 | `internal/secrets` | 不需要（文件被忽略） |
| 协议协商 | `negotiate()` | 不需要 |
| 游标 | `BindInfo.Cursor` | 换成 `lastCommit`（仅用于显示与快进判断） |

### 3.5 必须解决的 6 个工程细节

| # | 细节 | 不处理的后果 |
|---|---|---|
| 1 | **git 作者身份** | `git commit` 直接失败（"Please tell me who you are"）；应预检并给中文提示，不擅自改全局配置 |
| 2 | **add 白名单** | `git add -A` 会把用户自己放进目录的临时文件、`.tmp`、编辑器备份一起提交 |
| 3 | **YAML 冲突标记** | 冲突标记留在工作区 → 扫描器解析失败 → 条目"消失"，用户以为丢数据 |
| 4 | **换行/文件模式** | Windows `core.autocrlf` 会让"没改的文件"显示为改动，dirty 计数永远不清零；需读 `git config core.autocrlf` 或在文档中明确建议 `input/false` |
| 5 | **hooks** | 用户 `pre-commit`/`pre-push` 失败时，必须把原始 stderr 透出，不能只说"同步失败" |
| 6 | **凭证** | 不能自己存 token；依赖 credential helper / SSH key，失败提示要指向具体命令（`git credential fill`） |

## 4. 用户使用体验的异同

### 4.1 首次配置

| | 服务端 | Git |
|---|---|---|
| 需要输入 | 服务端地址、**项目 ID（手填）**、PAT | remote URL、分支、凭证（通常系统已有） |
| 找参数的难度 | 项目 ID 要去 Web 里翻（当前无"列出我的项目"接口调用） | clone URL 就在仓库页，复制即用 |
| 失败反馈 | "服务端返回 401/403"、"缺少同步能力" | "Permission denied (publickey)"、"not a git repository" |
| 心智负担 | 低（三个框） | 中（要理解 remote/branch） |

**现状的一个真实短板**：`SyncDialog.vue` 的 projectId 是 `n-input-number` 手填，没有项目选择器。这是服务端模式在"首次体验"上输给 Git 的地方。

### 4.2 日常

| | 服务端 | Git |
|---|---|---|
| 触发方式 | 状态栏/侧栏刷新 + 120s 定时（仅活动根） | 手动"同步"按钮，或定时 fetch |
| 用户看到的概念 | "已同步 / 有 N 处未推送 / 游标" | "领先 2 个提交 / 落后 1 个提交 / 有未提交改动" |
| 是否要理解 VCS | 否 | 是（未提交、rebase、冲突） |
| 出问题时的可解释性 | 中（Report 里有 errors 数组） | 高（每条 git 错误都能命令行复现） |
| 多根并存 | 每根独立绑定，但只有活动根自动同步 | 同上（同一调度器） |

### 4.3 冲突

这是体验差异最大的一处。

| 场景 | 服务端 | Git |
|---|---|---|
| 冲突提示 | 打开同步弹窗，列出每条冲突 | 同步失败 + 冲突列表 |
| 展示粒度 | 4 个字段的"本地 → 服务器" | 两份完整 YAML 对照 |
| 决策成本 | 低（逐字段看差异） | 高（要看整份文件） |
| 批量处理 | 「全部采用本地/服务器」 | 同样可做，但"全部采用远端"= 丢弃本地全部改动，风险更高 |
| 误操作恢复 | `.conflicts/` + `.trash/` | `.conflicts/` + git reflog（更强） |

对**非 git 用户**，服务端的字段级冲突明显更友好；对**开发者**，Git 的整文件取舍 + `git diff` 更符合直觉。这决定了 Git 模式不应取代服务端模式，而应作为可选项。

### 4.4 恢复与审计

| | 服务端 | Git |
|---|---|---|
| 误删恢复 | `.trash/`（本地） | `git checkout <commit> -- path`（跨设备、跨时间） |
| 谁改的 | `change_log.device/actor`（Web 端可查） | `git log/blame` |
| 回滚到某天 | ❌ 无历史 | ✅ `git log --before=` |
| CI 消费 | 需要调 API | ✅ 直接读仓库 |
| 代码评审 | ❌ | ✅ PR/MR |

### 4.5 四个场景走查

| 场景 | 服务端表现 | Git 表现 | 谁更好 |
|---|---|---|---|
| 两人同时改同一接口的 URL | 后 push 者拿到 conflict，字段级二选一 | rebase 冲突 → abort → 整文件二选一 | 服务端（粒度细） |
| 飞机上改 20 个接口，回来合并 | dirty 累积，一次 push；冲突逐条处理 | 本地 20 个 commit 或 1 个 commit，rebase 冲突逐文件处理 | Git（有历史、可分批） |
| 新人加入项目 | 要 PAT + 项目 ID | `git clone` 即可 | Git |
| 误删一个分组 | `.trash/` 恢复，仅本机 | 任意设备 `git checkout` 恢复 | Git |

## 5. 各自的问题与优势

### 5.1 服务端模式

**优势**

1. **细粒度冲突**：字段级 diff + 三选一，非技术用户也能处理。
2. **权限与审计**：`PermQuery/PermUpdate/PermDelete` + 含删除追加校验（`doc/客户端与服务端同步实现现状.md` §一.5）、`device/actor` 溯源、`client_write_enabled` 一键禁写。
3. **零环境依赖**：只要网络，不需要 git。
4. **secret 可控**：口令加密后出网，未设口令则不出本机。
5. **Web 端协同**：服务端数据可被 Web 直接展示/编辑（这是 Git 方案给不了的）。
6. **明确的失败语义**：`conflict/rejected/readonly` 分类，UI 可精确提示。

**问题（如实列出）**

| # | 问题 | 依据 |
|---|---|---|
| 1 | ~~首次配置要手填 projectId，无项目发现~~ **已于 2026-10-19 修复**：同步设置新增「获取项目」（`GET /api/project`，PAT 可访问） | `SyncDialog.vue`、`client.go:Projects`、`app_sync.go:ListServerProjects` |
| 2 | PAT 以明文存 `.sync.json` 且 UI 回显 | `client.go:35-37`、`SyncDialog.vue:84-85` |

| 4 | ~~**pull 覆盖本地改动时，仅 `api` 落冲突副本**，doc/example/variable 无副本保护~~ **已于 2026-10-19 修复**：doc/example/env 统一整文件快照（`.conflicts/`，可列出、可预览、可原样还原） | `engine.go:snapshotDocIfDirty` 等、`collection/conflict_snapshot.go` |

### 5.2 Git 模式

**优势**

1. **无损**：proto、gRPC、脚本、未知字段、附件全部按字节同步。
2. **历史与回滚**：commit、blame、reflog、按时间点恢复。
3. **CI/评审可消费**：PR、流水线、变更审计。
4. **零服务端成本**：不用部署、不用备份，远端用现成的 GitHub/GitLab/自建。
5. **离线体验完整**：本地 commit 即历史，不依赖"上次同步点"。
6. **分支即草稿**：可以用分支做接口改版的评审，这是服务端模式没有的能力。
7. **团队已有工作流**：不用教用户新工具。

**问题**

| # | 问题 | 影响 |
|---|---|---|
| 1 | 需要 git 可执行文件与凭证配置 | Windows 普通用户可能装不上/不会配 SSH |
| 2 | 冲突是整文件级，YAML 冲突标记会破坏解析 | 必须 abort，等于"全要或全不要" |
| 3 | 仓库级权限，无字段级/无权限审计 | 只读成员无法只读某分组 |
| 4 | 二进制/大文件让仓库膨胀 | proto、证书、截图需 LFS，而 LFS 在纯 Go 实现里支持差 |
| 5 | `.sync.json` 被忽略 → 每台设备需单独绑定 | 对 Git 是合理的（不同人可绑不同服务端），但用户会困惑"为什么克隆下来没同步" |
| 6 | secret 文件不同步 | 团队需另建渠道分发，否则新人跑不通 |
| 7 | 非技术用户不理解 rebase/未提交/游离 HEAD | 误操作风险高（如 `reset --hard`） |
| 8 | 与文件监听耦合：大批量 checkout 会触发大量事件 | 现有 300ms 防抖 + 全量 `RebuildIndex` 可承受，但大集合需实测 |

## 7. 是否存在更合适的同步方案

按"投入产出比"排序：

| 方案 | 机制 | 优点 | 缺点 | 适配度 |
|---|---|---|---|---|
| **A. 服务端 + Git 镜像（推荐）** | 服务端负责协作/冲突/权限；每轮成功同步后自动 `git commit`（可选 push）到本地仓库 | 拿到历史/回滚/CI/评审，不承担 Git 的冲突复杂度；几乎不改同步引擎 | 只是"单向留痕"，不能靠 Git 协作；需要在服务端同步后加一个 commit 步骤 | ⭐⭐⭐⭐⭐ |
| **B. Git 作为独立同步源（本文 §3）** | 二选一绑定，Git 全权负责 | 无损、离线强、零服务端 | 冲突粗、权限粗、有环境依赖 | ⭐⭐⭐⭐ |
| **C. 纯 Git-first（学 Bruno）** | 默认 Git，服务端降级为可选托管 | 最贴近"文件即真相源"的定位；CI 友好 | 放弃 Web 端协同与细粒度权限；对非 git 用户不友好 | ⭐⭐⭐ |
| **D. 文件同步盘（Syncthing/iCloud/OneDrive）** | 目录级同步 | 零开发 | 冲突产生"副本文件"，YAML 同样会坏；无历史；多端同时写极易丢改动 | ⭐⭐（仅个人多设备） |
| **E. WebDAV / S3 自研协议** | 自建文件树同步 + manifest | 可控 | 等于重写一个 Git（版本、冲突、并发），投入最大 | ⭐ |
| **F. CRDT（Yjs/Automerge）** | 字段级自动合并 | 冲突体验最好 | 需把所有条目模型化、引入二进制文档格式，破坏"纯文本 YAML + git 友好"，工作量最大 | ⭐（现在不做） |
| **G. 服务端 Webhook 导出到 Git** | 服务端单向推送 | 客户端零改动 | 只有服务端 → Git，没有反向；历史不含本地未推送改动 | ⭐⭐⭐（作为 A 的补充） |

**结论**：没有比"Git 作为可选同步源 + 服务端保留"更合适的**替代**方案。CRDT 与 WebDAV 都是重造轮子；同步盘不适合结构化文本；而 **A（服务端 + Git 镜像）是性价比最高的增强**，B 是更彻底但更贵的选择。

## 8. 推荐方案

### 8.1 分层

```
        ┌──────────────────────────── App 门面 (app_sync.go) ────────────────────────────┐
        │  BindInfo.Kind = "server" | "git"   一个集合同一时刻只有一个 Kind 处于 active     │
        └───────────────┬─────────────────────────────────────┬───────────────────────────┘
                        │                                     │
        ┌───────────────▼──────────────┐      ┌───────────────▼──────────────────────────┐
        │ syncengine（现状，不动）      │      │ gitsync（新增）                           │
        │ 游标/增量/op_id/base_rev      │      │ fetch/pull(ff-only|rebase)/commit/push    │
        │ 字段级冲突 + .conflicts/       │      │ 整文件冲突 → abort → ours/theirs 副本      │
        └───────────────┬──────────────┘      └───────────────┬──────────────────────────┘
                        │                                     │
        ┌───────────────▼─────────────────────────────────────▼──────────────────────────┐
        │ 共用：collection 文件层 / index 索引 / watch 监听 / .conflicts / 状态栏 / 定时器   │
        └────────────────────────────────────────────────────────────────────────────────┘
```

三条硬约束：

1. **单写通道**：`BindInfo.Kind` 单值，同一集合不允许 server 与 git 同时写。若要"服务端 + Git 镜像"，Git 侧只允许 `commit`（本地留痕），**禁止自动 push 到共享分支**，除非用户显式开启。
2. **工作区永远可解析**：任何冲突都 abort，绝不把 `<<<<<<<` 留在 `*.yml` 里。
3. **不做 YAML 语义合并**：与现有"不做字段级三方合并"的边界保持一致。

### 8.2 分阶段

| 阶段 | 内容 | 产出 | 优先级 |
|---|---|---|---|
| **P0（前置修复）** | 修 `saveLocalIfDirty` 只覆盖 `api` 的不对称（doc/example/variable 也要留副本）；给 SyncDialog 加"项目发现" | ✅ **已完成（2026-10-19）**：`collection/conflict_snapshot.go` 通用快照 + `syncengine` 拉取前留底；`ListServerProjects` + 项目下拉。**另于同日补修两条评审发现的既有缺陷**：`pushDirty` 早退导致"只改文档/示例/环境不推送"（评审 P0-4）、`.gitignore` 已存在时不补忽略项导致 PAT 可能入库（评审 P0-5） | 必做 |
| **P1（验证需求）** | Git 只读模式：检测仓库、fetch、展示 ahead/behind 与 diff、不写 | 用最小成本验证"用户是否真的需要 Git" | 建议先做 |
| **P2（核心）** | Git 双向：commit/push/rebase/abort + 冲突二选一 + 绑定 UI + 状态栏 + e2e | 可用的 Git 同步源 | 主体 |
| **P3（增强）** | 服务端同步后自动 commit 到本地 Git（方案 A 的"镜像"）；可选 PR 工作流 | 历史/回滚/CI 能力 | 可选 |

### 8.3 明确不做

| 不做 | 原因 |
|---|---|
| 同一集合双源同时写 | 两套冲突模型必然互相覆盖 |
| YAML 字段级三方合并 | 工作量 ≈ 重写 diff/merge；与既定边界冲突 |
| 内嵌 go-git（首版） | 行为差异带来的支持成本高于"依赖 git"的成本 |
| LFS / submodule / shallow clone | 边缘场景，跨平台差异大，收益低 |
| CRDT / WebDAV | 重造轮子，破坏纯文本定位 |
| 自行保存 Git 凭证 | 应交给系统 credential helper/SSH agent |

### 8.4 验收标准（建议）

1. `git` 不在 PATH 时，绑定页给出明确中文提示与安装指引，不崩溃。
2. 本地有未提交改动时点同步：自动 commit → rebase → push；冲突则 abort 且工作区可正常打开。
3. 冲突后 `.conflicts/` 出现 ours/theirs 两份，UI 可选择且选择后能提交。
4. 远端删除了本地修改过的文件：给出 modify/delete 冲突提示，不静默删除。
5. CRLF 仓库（`core.autocrlf=true`）下，未修改文件不被计为 dirty。
6. `bash scripts/check.sh` 通过；新增 `gitsync` 单测 + 一个真实临时仓库的集成测试。
7. 同一集合切换到 `kind=git` 后，原 `.sync.json` 的服务端字段保留但不生效（可切回）。
