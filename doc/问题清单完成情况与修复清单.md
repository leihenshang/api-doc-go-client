## 二、软删除实现方案（B-06）

### 2.1 现状诊断：不是"要不要做"，是"做了一半"

| 层面 | 现状 | 证据 |
|---|---|---|
| 读取侧 | 仍在过滤 `is_deleted = 0` | `repository/repository.go:40` `active()`；`content.go:120,140,151,187` 等 10 余处 |
| 索引侧 | 8 处局部唯一索引**已按软删除设计** | `model/{api,group,business,variable,project,share,api_return_sample}.go` 均带 `where:is_deleted = 0` |
| 写入侧 | 大部分实体硬删 | `DeleteGroup/DeleteApi/DeleteDoc` 等 10 处走 `gmHardDelete` |
| 仓储辅助 | **恢复所需的查询已经写好了** | `ApisByIDsAny`（含已删除）、`DocsByIDsAny`、`GroupsByProjectsAny`（注释写明「供恢复时回溯父级链」） |
| 接口侧 | 前端已调用，服务端 0 条路由 | `web/src/api/content.ts:99,104,191,196` 调 6 个端点；服务端 grep `restore\|purge` 只命中 1 行注释 |

**结论：仓储层的砖已经砌好了，缺的是 service + handler + router 这三层。**

### 2.2 已造成的两个故障

1. **回收站「还原」按钮 404** —— 前端 6 个端点（`/api/api/restore`、`/api/api/restore-batch`、`/api/api/purge-batch`、`/api/doc/restore`、`/api/doc/restore-batch`、`/api/doc/purge-batch`）服务端全无
2. **僵尸数据只进不出** —— 导入「完全覆盖」时 `SoftDeleteApisByProject` 把旧接口置 `is_deleted=1`，被 `active()` 隐藏且无 purge 路由 → 永久堆积

### 2.3 设计

**范围**：`api` / `doc` 两类进回收站（连带 `group` 祖先链恢复）——对齐 `AGENTS.md` T20。其余实体（bug / field-mapping / property / share / variable / example）**维持硬删除**，并在文档中写明「不在回收站范围」。

**数据模型**：零迁移。
- 复用 `BaseModel.IsDeleted int8`（0 正常 / 1 回收站），两方言的 `is_deleted` 列均已在 `0001_init` 存在
- 唯一索引已带 `where:is_deleted = 0`，软删后不占用唯一槽位

**状态机**：

```
正常(0) --DELETE--> 回收站(1) --restore--> 正常(0)
                       |
                       +--purge--> 物理删除（不可恢复）
```

**分层改动**：

| 层 | 改动 |
|---|---|
| `repository/generic.go` | 新增 `getActive` / `gmSoftDelete` / `gmRestore` / `gmPurge` 四个泛型助手 |
| `repository/content.go` | `DeleteApi/DeleteDoc/DeleteGroup` 由 `gmHardDelete` 改 `gmSoftDelete`；`GetApi/GetDoc/GetGroup` 加 `is_deleted=0`（详情/更新自动拒绝已删项）；新增 `GetApiAny/GetDocAny/GetGroupAny`、`RestoreApis/RestoreDocs/RestoreGroups`、`PurgeApis/PurgeDocs` |
| `service/content.go` | 新增 `RestoreApis/RestoreDocs/PurgeApis/PurgeDocs`；恢复需 `PermUpdate`、彻底删除需 `PermDelete`；逐条校验项目归属，跨项目 id 直接拒绝；恢复时向上收集**已软删的祖先分组链**一并恢复；返回 `RestoreResult{restored, groups}` |
| `handler/content.go` | 新增 6 个处理器，`{id}` 走 `dto.IDReq`、`{ids}` 走新增 `dto.IDsReq` |

**同步侧：零改动。** 三条依据：
1. `ListApisAll` / `ListGroupsAll` / `ListDocsAll` 注释明确「含软删」且**不过滤**，payload 已带 `Deleted: IsDeleted == 1` → 客户端据此移入 `.trash/`
2. `applyUpsert` 六个分支已有 `e.IsDeleted = model.IsDeletedNo` → 再次 upsert 自动复活
3. `applyDelete` 调用同一批 repository 方法 → 跟随改为软删，自动一致

**风险与对策**：

| 风险 | 对策 |
|---|---|
| 硬删的历史数据不可恢复 | 只能保证今后；发布说明中注明 |
| 软删 group 后子项变孤儿（`group_id` 指向已删组） | 与现有硬删行为一致，不新增问题；恢复条目时祖先链一并恢复，孤儿自动归位 |
| 批量接口被放大调用 | 单批上限 200 条（与 `page.Normalize` 一致）；跨项目 id 拒绝 |
| 回收站列表同样分页 | 复用现有 `deleted=1` 查询，无需改动 |

**验收标准**：

1. 删除接口 → 列表消失、回收站出现、DB 行仍在且 `is_deleted=1`
2. 还原 → 回到列表；所属已删分组（含祖先链）一并恢复
3. 彻底删除 → DB 行消失，回收站不再可见
4. 客户端删除 → 服务端软删（不再物理消失）；服务端软删 → 快照带 `deleted=true` → 客户端移入 `.trash/`
5. `gofmt` / `go build` / `go vet` / `go test` 全绿

## 五、P0 修复记录（2026-10-17）

### 5.1 诊断修正：不是「postgres 缺一个文件」，是「双方言都断链」

原分析 2 说「postgres 迁移缺 `0010_sync_foundation`」。实测后这个描述**偏轻**，真实情况有三层：

| 层 | 事实 |
|---|---|
| postgres 少一份迁移 | `migrations/postgres/` 从 `0009_user_lang` 直接跳到 `0010_token_cipher`，而 sqlite 的 `0010` 是 `sync_foundation`。**编号仍然连续**，所以看不出缺口 |
| 连带文件整体错位 | postgres 的 `0010_token_cipher`…`0013_var_sync_identity` 实际对应 sqlite 的 `0011`…`0014`，逐份内容一致（已 diff 逐条核对），只是编号少 1 |
| 断链的直接后果 | postgres 侧从未创建 `user_token` 表，而 `0010_token_cipher` 的第一句就是 `ALTER TABLE "user_token" ADD COLUMN token_cipher` → **必然报 `relation "user_token" does not exist`，整条链在半途中断**，DB 停在半迁移状态 |
| **sqlite 侧也跑不通** | `0010_sync_foundation.up.sql` 写的是 `id BIGINT PRIMARY KEY AUTOINCREMENT`。SQLite 规定自增主键只能是 `INTEGER PRIMARY KEY AUTOINCREMENT`，实测报 `AUTOINCREMENT is only allowed on an INTEGER PRIMARY KEY`；即使跳过这句，`0011_token_cipher` 同样因为没有 `user_token` 而失败 |

**实测证据**（按版本号顺序把 up 脚本喂给真实 SQLite）：

```
OK 0001…0009
FAIL 0010_sync_foundation.up.sql -> AUTOINCREMENT is only allowed on an INTEGER PRIMARY KEY
```

### 5.5 W-05 用户管理提权（2026-10-17）

**原描述**：「用户管理页无管理员门禁，可提交 `type:3` 超管」。核对代码后确认是**三条独立漏洞**，只补前端门禁并不够：

| # | 位置 | 问题 |
|---|---|---|
| 1 | `service/auth.go` `UpdateUser` | 只用 `isAdmin(2/3)` 放行 `type`，于是**管理员（2）可以把任何人（含自己）改成超管（3）**——admin ⊂ superuser，这是一条现成的提权链 |
| 2 | `service/auth.go` `ListUsers` | **零权限校验**，任何登录用户都能拉整张 `user_info`，含 `email`/`mobile_number`/`last_login_ip`/`last_login_time` |
| 3 | 前端 `projectNav.ts` + `router/index.ts` | `properties` 页签有 `adminOnly`，`users` 没有；且两条路由都没有 `requiresAdmin`，**只藏页签挡不住手输 URL** |

**为什么不能简单给 `ListUsers` 加管理员校验**：`listUsers` 被 `BugView`、`ProjectOverviewView`、`composables/userNames.ts` 三处调用，用于把 user_id 映射成显示名（备忘清单指派、作者/操作人回显）。限制成管理员专用会直接打断这些普通用户功能。故改为**字段级脱敏**。

**改动**：

| 层 | 改动 |
|---|---|
| `service/auth.go` | `ListUsers` 增加 `operator` 入参；非管理员时清空 `Email`/`MobileNumber`/`LastLoginIP`/`LastLoginTime`，保留 `name`/`nick_name` |
| `service/auth.go` | `UpdateUser` 在赋值**之前**调 `ensureAccountChangeAllowed`（先写后校验会让失败路径把改动带出去）；新增该辅助函数实现三条边界 |
| `handler/user.go` | `ListUsers` 传入 `principal` 构造的 operator |
| `web/composables/projectNav.ts` | `users` 页签补 `adminOnly: true` |
| `web/router/index.ts` | `users` / `properties` 路由补 `requiresAdmin: true`；`beforeEach` 增加管理员判定，不通过重定向到项目列表 |
| `web/views/user/UserManagerView.vue` | 角色下拉按当前账号等级裁剪（管理员看不到「超级管理员」）；超管行对其他管理员禁用「编辑」；表格标签改用独立的 `ROLE_LABELS`（不能复用被裁剪后的下拉，否则超管行会显示成数字 3） |

**三条越权边界**（`ensureAccountChangeAllowed`）：

1. 非管理员不得改任何人的角色或状态
2. 管理员不得动超管账号，也不得调整任何角色（角色只有超管能给）
3. 超管不能改自己的角色（唯一超管一旦自降，系统再无人可管）；且角色取值必须在 1~3 内

判定按「**是否真的变**」比较（`req.Type != target.Type`），而非 `req.Type > 0`：前端保存资料会把当前 `state`/`type` 原值一起回传，按 `>0` 判定会让普通用户改昵称也被拦。

**新增测试**（`internal/service/user_role_test.go`）：

| 测试 | 覆盖 |
|---|---|
| `TestRoleChangeGuards` | 普通用户自提权 / 自改状态、管理员自提超管 / 改他人角色 / 停用超管、超管自降角色 —— 6 条路径全部拒绝；超管提升他人角色成功且落库；`type:9` 被拒 |
| `TestUpdateOwnProfileNotBlocked` | 普通用户改自己昵称、管理员改他人昵称，且 `type`/`state` 原值回传时不误拦 |

## 七、第二轮修复记录（P1 / P2，2026-10-17）

### 7.1 B-15 覆盖导入不再「先删后失败」

三种导入（OpenAPI / Postman / Bruno）的 `overwrite` 策略原本是「先清空项目现有接口与接口目录，再逐条写入」，两段各自提交。中途任何失败都会留下**一个被清空且只导入了一半的项目**。`ImportOpenAPI` 更严重：它先 `prepareImport`（清空）再 `Decode`，文档解析不了就直接返回——等于用户选错一次文件就丢光整个项目。

改法：

1. **先解析、后动数据**（OpenAPI 补齐，另两者本来如此）；
2. 清空与写入收进 `s.repo.Transaction`，任一硬错误整体回滚；
3. 新增 `importScope{ctx, repo}`，让 `prepareImport` / `resolveGroup` / `postmanGroupEnsurer` / `brunoGroupEnsurer` 拿到**事务句柄**（此前直接摸 `s.repo`，写不进事务）；
4. 顺手修 `resolveGroup`：`existing []model.Group` 按值传递，新建分组写不回调用方，**同一份文档里重复出现的 tag 每出现一次就再建一个同名分组**。改传指针。

守卫测试 `internal/service/import_tx_test.go` 四个用例：非法 body + overwrite 时旧接口仍在（OpenAPI/Postman 各一遍）、覆盖成功后旧接口消失、3 个 op 共用 tag 只建 1 个分组、带 path 级 summary/parameters 时不产生幽灵接口。

### 7.2 B-12 变更流水与修订号同事务

`appendChangeTx` 把 `AppendChange` + `SetLastChange` 放进一个事务，`ctx` 经 `context.WithoutCancel` 脱钩（客户端断开不该让审计流半途中断）。`sync.go` 8 处与 `variable.go` 的 `logVarChange` 统一走它；写入失败时该条返回 `rejected` 而不是 `ok`，客户端 `applyPushResults` 会把条目留在 dirty 队列下次重试。

`change_log_test.go` 用未知实体类型强制 `SetLastChange` 报错，断言 `change_log` 条数为 0——证明整体回滚，而不是「流水落了、版本号没推」。

### 7.3 W-16 结论：只修解析，不改存储形态

- **已修**：`stores/user.ts` 的 `loadFromStorage` 加 try/catch + 结构校验（token 必须是非空字符串），异常时清掉脏数据回落未登录。pinia 的 state 在模块求值期构造，原来一个损坏的 `userInfo` 就能让整个应用白屏且无自助恢复路径。
- **不改**：token 仍存 localStorage。该项目是「同一份前端同时跑在浏览器与 Wails 桌面端」的形态，改 httpOnly Cookie 会让桌面端（自定义协议 + 本地服务）失去可行的凭证通道，改造面远大于收益。过期由服务端 `jwt.Parse` 校验 + 前端 401 拦截器 `clear()` 兜底。

### 7.4 B-11 分层归位
