## P0 — 搜索与读取（收益最大）

### T1 `search_requests` 支持精确匹配与上下文片段
- **问题**：分词模糊匹配误报严重。实测搜整词 `ministryreportingunits` 返回约 50 条命中，正文真含该词的仅 1-2 条，被迫逐张 `get_request_detail` 人工确认
- **方案**：
  1. 新增 `exactMatch: boolean`（默认 false）：true 时整词匹配，不走分词
  2. 新增 `fields: string[]` 限定搜索范围，可选 `uri` / `docs` / `respDoc` / `bodyFields`，缺省搜全部
  3. 每条命中附带 `snippet`：匹配行及前后各 1 行，单条上限约 200 字符
- **验收**：`query=ministryreportingunits&exactMatch=true` 仅返回正文真含该词的卡片，snippet 可直接看出命中位置
- **状态：已完成** —— `exactMatch`（ASCII 词边界整词，中文/标点/斜杠算边界）、`fields`（name/uri/docs/respDoc/bodyFields/header/body，未知值报错并列可选值）、`snippet`（命中行±1，200 字符）均已实现并渲染；另修掉「深读后 0 分候选仍被当结果返回」的旧行为。
  - 回归：`TestSearchRequestsExactFieldsAndSnippet`
  - 已知限制：`fields` 只保留 `docs`/`respDoc`/`bodyFields` 等正文类字段时，候选来自「深读窗口」（默认前 60 个索引节点）；超大集合建议先用名称/URL 缩小范围，或加大 `enrichLimit`（`internal/mcp/service.go`）。

### T2 新增文档内容搜索
- **问题**：独立文档（docs 模块）无内容级搜索，8 篇文档只能逐篇 `get_doc` 全文拉回（6-12KB/篇）人肉扫
- **方案**：新增 `search_docs(project, pattern, exactMatch?)`，返回 uid、路径、命中行号、snippet；或并入统一入口 `search(scope: "requests" | "docs" | "all")`
- **验收**：一次搜索能定位所有含目标词的文档及行号
- **状态：已完成** —— 新增工具 `search_docs(project?, pattern, exactMatch?, limit?)`：按行返回 `L<行号>: 片段`（每篇最多 5 处，其余提示用 `get_doc`），结果按命中行数排序并带 uid/路径。
  - 回归：`TestSearchDocsTool`
  - 说明：选择「独立工具」而非并入 `search(scope)`，保持现有 `search_requests` 契约不动。

### T3 `get_request_detail` 支持分段读取
- **问题**：说明文档、body 字段表、respDoc（最多 38 行）、响应样例、示例列表全拼在一个响应里，实测 3 次超 5000 字符被截断（5830 / 6984 / 6754）
- **方案**：新增 `sections: string[]`，可选值 `overview` / `docs` / `bodyFields` / `respDoc` / `examples`；不传 = 现状全量
- **验收**：`sections=["docs"]` 时单卡响应 <3000 字符；不传参数时响应与现状一致
- **状态：已完成** —— 分段渲染（身份行恒输出，其余按段过滤）；未知取值直接报错；不传 = 全量（旧行为逐字一致）。`sections=["docs"]` 用例实测远小于 3000 字符。
  - 回归：`TestDetailSectionsAndFullHash`

## P1 — 更新安全与效率

### T4 批量读取卡片
- **问题**：31 张卡片逐个调用，20+ 次往返
- **方案**：新增 `get_request_details(project, uids: string[], sections?: string[])`，单次上限 10 个 uid（超限明确报错），响应按 uid 分组
- **验收**：一次调用可取多张卡片的指定段
- **状态：已完成** —— 新增工具 `get_request_details`：`uids` 1–10（0 个或 >10 直接报错并提示分批），复用 `get_request_detail` 的全部参数（sections/includeBody/maxBodyBytes/query），结果按 `===== uid =====` 分组，单个失败不影响其它并输出「成功 N / M」。
  - 回归：`TestBatchRequestDetails`

### T5 hash 显示完整化
- **问题**：`get_*` 返回的 hash 带省略号（如 `da95d6f21183…`），无法确认能否直接回传 `ifMatch`
- **方案**：统一返回完整 hash；若保留截断显示，须在工具描述中写明“截断 hash 可直接用于 ifMatch”
- **验收**：`get_request_detail` / `get_doc` 返回的 hash 直接回传 `update_request` / `update_doc` 的 `ifMatch` 可成功
- **状态：已完成（按决策 3-D：搜索侧加开关）** —— `get_request_detail` 与 `get_doc` 输出完整 hash；
  另给 `search_requests` 增加 `includeHash`（默认 false 省体积；true 时每条结果附完整 hash，可直接回传 ifMatch）。
  - 回归：`TestDetailSectionsAndFullHash`（长度/无省略号）、`TestSearchRequestsExactFieldsAndSnippet`（开关）

### T6 文档局部替换
- **问题**：`docs` 只能整篇覆盖，6.7KB 文档需先抄原文再全量重写，抄写过程任何截断都会丢内容
- **方案**：`update_request` / `update_doc` 支持 `replaces: [{old, new, replaceAll?}]`；`old` 未匹配时报错且**不落盘**；与现有全量覆盖模式并存
- **验收**：局部替换后其他段落逐字节保留；`old` 找不到时返回明确错误
- **状态：已完成** —— `update_doc.replaces` 作用于正文、`update_request.replaces` 作用于说明文档（docs），`replaceAll=true` 替换全部、默认首处；任一 `old` 找不到即整单拒绝（写盘前计算）；与 `content`/`docs` 同时传会报「互斥」；`section=docs` 下允许 `replaces`。
  - 回归：`TestUpdateDocReplacesPreviewAndConflictHash`、`TestUpdateRequestReplacesDocs`

### T7 更新响应附带落盘摘要
- **问题**：`update_*` 成功只回一行 hash，确认写入必须再调一次 `get_*`
- **方案**：更新响应附带保存后正文前 5 行，或改动行 ±1 的 diff 摘要
- **验收**：update 后从响应即可确认目标改动已生效
- **状态：已完成（按决策 4-C：智能混合）** —— 动过 content/docs/replaces 时，成功响应附「落盘确认」：
  能按行定位改动（共同前缀/后缀夹出区间）→ 标注「第 N–M 行 ±1 行」并给出改动区片段（≤400 字符）；
  整篇重写/首次写入 → 回落「前 5 行」。实现在 handler 层（先读旧文本再 update，避免改动 Service 签名影响 20+ 调用点）。
  - 回归：`TestUpdateDocReplacesPreviewAndConflictHash`、`TestUpdateRequestReplacesDocs`（断言改动行标注）

## P2 — 体验细节

### T8 `ifMatch` 冲突语义明确
- **问题**：提示 hash 可回传 `ifMatch`，但冲突时是报错还是静默覆盖未说明，多端并发编辑无底
- **方案**：`ifMatch` 不匹配时返回明确错误码 + 当前最新 hash；工具描述写清传 / 不传 `ifMatch` 两种行为
- **验收**：并发冲突收到明确报错，不发生静默覆盖
- **状态：已完成** —— 冲突统一改为 `ifMatch 不匹配：<请求/文档> <uid> 已被外部修改，本次未写入任何内容。当前 hash=<完整 hash>，请重新读取后合并再试；不传 ifMatch 可强制覆盖`；`update_request` / `update_doc` 描述写明两种行为。
  - 回归：`TestUpdateDocReplacesPreviewAndConflictHash`（bogus ifMatch → 报错含当前 hash）

### T9 `get_project_modules` 过滤结果收敛
- **问题**：`query=部侧` 时 12 个 0 命中的无关模块也列出
- **方案**：带 query 时默认只返回有命中的模块；或加 `onlyMatched: boolean`
- **验收**：`query=部侧` 只返回 8 个相关模块
- **状态：已完成（按决策 1-C：默认收敛 + 汇总行）** —— 带 query 时**默认只返回有命中的模块**（模块名/路径命中，或其下有命中请求）；
  `onlyMatched=false` 可显式查看全部模块；汇总行始终给出「共 N 个模块（有命中 M 个）」。
  - 说明：这是对默认输出语义的主动调整（放弃「不传参数行为不变」），已在工具描述与手册里写明。
  - 回归：`TestProjectModulesOnlyMatched`（默认收敛 / false 看全量 / 汇总行）

### T10 截断提示与实际参数对齐
- **问题**：超限截断提示建议“使用 pagination 参数”，但 inputSchema 中不存在该参数
- **方案**：补上分页参数，或将提示改为实际可用的减体积手段（`maxBodyBytes` / `sections`）
- **验收**：截断提示中提到的每个参数都能在 inputSchema 中找到
- **状态：已完成** —— 现状代码里已无 `pagination`（不存在该提示），但提示文案写的是 `include_body`（真实参数是 `includeBody`）。已统一改为：`要更多内容请调大 maxBodyBytes，或用 get_request_detail 的 sections 只取需要的分段 / includeBody 取全文`；`renderSend` 的 `include_body=false` 也改为 `includeBody=false`。
  - 回归：`TestTruncateNoteMentionsRealParams`（正向断言三个真实参数、反向断言不出现 `分页/pagination/include_body`）
