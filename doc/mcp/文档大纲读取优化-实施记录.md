# 文档大纲 / 分段读取优化（P0–P2 实施记录）

> 目标：让 MCP 用**几百 token** 判断一篇文档讲什么、哪一节相关，再按需精读，而不是一上来吞全文。
> 完成时间：2026-11-06

## 1. 起因：现有 `outline` 其实没省 token

`get_doc` 早就支持 `outline=true` 与 `startLine/maxLines`，但结构化输出一直写死：

```go
// 旧代码
return renderDocDetail(d, view), docDetailData(in.Project, d, true), nil
//                                                              ^^^^ 永远带全文
```

文本被截断了，`structuredContent` 里仍是整篇 `content`。客户端只要读结构化内容（多数 AI 客户端都会），省 token 就完全失效。这是本次最先修的点。

## 2. 改了什么

### P0 · 结构概览（outline+）与口径统一

- 新增 `internal/mcp/docoutline.go`：标题提取、行范围、每节首句（60 字）、代码块/表格计数、按层级过滤、按标题定位、进程内缓存。
- `buildDocView` 成为**唯一读取出口**：文本与结构化输出同源，任何模式都不会偷偷带全文。
- `outline=true` 升级为「结构概览」：
  - `depth`（默认 **2**，最大 6）：更深层级只给数量（`omitted`）
  - `leads`（默认 true）：每节首句，关掉只剩标题
  - 行范围只覆盖「该标题自己的正文」（到第一个子标题为止），子标题单独成项
- **首次调用仍返回全文**（用户决策）：超过 **8000 字符**时，在正文**末尾追加**一句建议（不截断），并在结构化输出给 `hint`。

### P1 · 按标题读 + 搜索定位

- `get_doc(heading="安装", headingIndex=2)`：只返回该节（到下一个同级/更高级标题之前），支持同名第 N 个、`## 安装` 前缀、空白归一。
- `search_docs` 的每条命中补 `headingPath`（如 `设计 > 背景 > 现状`），命中后可直接跳读该节。

### P2 · 列表级概览 + 缓存

- `list_docs(withOutline=true)`：每条附标题清单（到 h2、最多 12 条），先挑文档再精读。
- 大纲缓存：`key = uid + 正文哈希`，正文一变自然失效；上限 128 条 FIFO。不落盘、不同步——文档会被 git pull / 同步 / 其它编辑器改，落盘必然陈旧。

## 3. 为什么不出「存一份大纲」

- MCP 要的是**当前正文**的结构，派生成本与读正文同级（本来就要读全文）；
- 文档可被外部修改，存下来的大纲会漂移；回写又会把文件弄脏、触发同步与 watcher；
- 因此：**派生 + 进程内缓存**，零迁移、零同步、永不错位。

## 4. 实测（开发版 devserver + 真实 MCP HTTP 会话）

样本：`doc/多同步源支持可行性与设计方案-评审.md`，**46,598 字符 / 663 行 / 38 个标题**（1 个 h1、7 个 h2、30 个 h3）。

| 读取方式 | 返回字符 | 相对全文 | 约 token（字符/1.5） |
|---|---|---|---|
| 全文（默认） | 46,882（含建议句） | 1× | ~31,255 |
| `outline=true`（depth=2） | **780** | **60.1×** 更小 | **~520** |
| `outline=true&depth=3` | 4,035 | 11.6× | ~2,690 |
| `outline=true&depth=3&leads=false` | 2,182 | 21.5× | ~1,455 |
| `heading="2. 正确性问题清单"` | 18,525 | 2.5× | ~12,350 |
| `list_docs(withOutline)` 单条标题 | 8 条标题（约 150 字符） | — | ~100 |

同时核对：

- `outline` 的结构化输出 **不含 `content`**（`hasContent=false`）；
- 全文模式 `kind=full` 且带 `hint`（"本篇 46598 字符 / 663 行（76.0 KB）：下次可先看结构…"）；
- 按标题读取 `kind=range`，`startLine=204 / endLine=389 / totalLines=663`，且 `content` 只含该节；
- `search_docs` 命中带 `headingPath`；`list_docs` 默认不带 `headings`（避免列表膨胀）。

> 说明：`2. 正确性问题清单` 这一节本身有 186 行、1.8 万字，属极端情况；此时应用 `startLine+maxLines` 继续分段。

## 5. 工具面变化（对外契约）

| 工具 | 新增 | 说明 |
|---|---|---|
| `get_doc` | `depth`、`leads`、`heading`、`headingIndex` | 默认仍是全文；`outline` 与 `heading` 互斥 |
| `get_doc`（输出） | `kind`、`lines`、`chars`、`startLine`、`endLine`、`totalLines`、`hint`、`depth`、`omitted`、`headings[]` | 大纲模式不带 `content` |
| `list_docs` | `withOutline`（入参）、`headings[]`（输出） | 到 h2、最多 12 条 |
| `search_docs`（输出） | `matches[].headingPath` | 「设计 > 背景 > 现状」 |

`tools/list` 体积 71,104 字节。原预算 70,000 装不下完整的新增字段，一度把 `leads` / `headingIndex` 的
说明与输出 schema 里的 `headings` 等字段压掉；确认「这是每个会话的固定成本、但换来读长文档时省几个数量级的
token」后，预算放宽到 **75,000**（约 5% 余量，见 `TestToolsListBudget`），schema 恢复完整。
schema 快照已按契约更新（`-update`），`doc/mcp/schemas/` 下的 `get_doc.json` / `list_docs.json` 有变更。

## 6. 测试

新增/调整（`internal/mcp`）：

- `docoutline_internal_test.go`
  - 大纲提取：围栏代码不算标题、首句跳过代码/表格/引用、行范围与代码块/表格计数
  - `depth`/`omitted`（depth=2 展开 3 个、隐藏 1 个）
  - 按标题定位：范围到同级/更高级标题之前；同名第 N 个；找不到时列可用标题；`##  安装 ` 归一
  - 结构化输出：outline 无 `content`、range 只给该节、full 原样 + 未超阈值无 `hint`
  - `headingPathAt` 三级路径；缓存同正文命中、正文变化重算
- `docoutline_test.go`（真实 MCP 会话）
  - `get_doc(outline)`：`kind=outline`、无 `content`、默认 3 个标题 + `omitted=1`、`depth=3` 展开 4 个、`leads=false` 无首句
  - `get_doc(heading)`：只返回该节（含子标题、不含下一节）；找不到报错；与 `outline` 互斥
  - `search_docs` 的 `headingPath`；`list_docs(withOutline)` 有/无 `headings`
  - 超长全文：内容完整 + `hint`；大纲输出体积守卫（≥3× 且不含小节末尾正文）
- 原有用例：长文提示改为按字符阈值；`ListDocs` 签名变更同步

门禁：`bash scripts/check.sh` 全绿（format → analyze → test → build → xcheck）。

## 7. 已知边界

- 只认 ATX 标题（`#`），不支持 Setext（`===` 下划线）；缩进代码块（4 空格）里的 `#` 仍会被当成标题。
- 标题文本不剥离行内标记（`**加粗**` 会原样出现在大纲里）。
- 首句是「第一段非空行」的截断，不是语义摘要；需要语义摘要时由调用方自己读该节。
- 缓存仅在单进程内有效；MCP 服务重启后首次读取会重新计算（毫秒级）。
