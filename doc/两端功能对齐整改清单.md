# 两端功能对齐整改清单（客户端 ⇄ 服务端）

> **范围**：`api-doc-go-client`（桌面客户端 + 内嵌 MCP）、`api-doc-go`（服务端 + Web）、`api-doc-go-share`（共享契约）。
> **方法**：以代码为准核对——服务端路由与模型（`server/internal`）、同步协议真源（`share/syncapi`）、客户端同步引擎（`internal/syncengine`）与集合模型（`internal/collection`）；文档仅作参考（服务端 `doc/功能清单.md` 描述的是旧架构，已失效并已标注）。
> **原则**：改动**不破坏既有契约**——新增键一律「缺键不动、空串清空」，旧客户端/旧服务端互操作行为不变。
> **进度**：⬜ 待做 ｜ 🟡 进行中 ｜ ✅ 已完成 ｜ ⛔ 判定不做（附理由）

|---|---|---|---|

## 二、整改项与进度

### R1　服务端修订历史不含客户端同步写入　【高】　✅ 已完成

- **现象**：服务端 `saveSnapshot` 只在 Web 保存路径调用（`service/content.go`），`service/sync_apply.go` 全文无调用。
- **影响**：Web 端「历史修订」看不到任何客户端改动；在 Web 回滚到旧版本会把客户端所有改动一起吞掉；协作审计链断裂。
- **落地**：
  - `server/internal/model/snapshot.go`：新增 `SnapshotActionSync = "sync"`。
  - `server/internal/service/snapshot.go`：拆出 `saveSnapshotWith(ctx, r, ...)`，可指定仓储句柄；同步路径传**事务句柄**，让快照与业务写入同生共死（否则事务未提交时快照已落库，revision 指向不存在的变更流水）。
  - `server/internal/service/sync_apply.go`：api / doc 分支 upsert 成功后写快照，payload 用 `model.Api` / `model.Doc` 全量 JSON（与 Web 路径同构，`restoreApiSnapshot` 可直接回滚）。
  - `web/src/components/RevisionHistory.vue` + i18n（zh-CN / en-US）：动作 `sync` 显示「客户端同步」。
- **单测**：`server/internal/service/sync_snapshot_test.go` —— `TestSyncPushWritesRevisionSnapshot`（同步写入留快照、动作=sync、可回滚回首次内容）、`TestSyncPushDocWritesRevisionSnapshot`。
- **状态**：✅ 已完成

### R2　全局变量（scope=3）不在项目同步范围　【高】　✅ 已完成（UI 待排期）

- **现象**：同步取数 `listProjectRowsPage` 只按 `project_id` 过滤（`repository/sync_page.go`），管理员维护的全局变量 `project_id=0`，既不进 `/sync/changes`（change_log 按项目过滤），也不进 `/sync/snapshot` 的按项目取数。
- **影响**：客户端解析 `{{var}}` 拿不到全局变量 → 同一请求在 Web 与客户端跑出不同结果。
- **落地**：
  - 协议：`syncapi.Payload` 新增 `scope` 键（1=请求级 2=项目级 3=全局）。
  - 服务端：`service/sync.go` 新增 `globalVarItems`，在增量与全量响应里**额外全量附带**全局变量（数量个位数，成本可忽略；快照附加行不计入分页序列，`HasMore` 仍按真实行数算，避免提前结束分页而漏拉数据）；`varSyncPayload` 带上 `scope`。
  - 客户端：新文件 `internal/collection/globals.go`（集合根 `globals.yml` 读写）；`internal/syncengine/globalvar.go` 分流（`scope=3` → 落 globals.yml，不进环境文件）；`internal/app/env.go` 合并全局变量，**优先级低于环境变量**；客户端不回推（服务端权威）。
  - **补强（端到端联调发现）**：客户端 `pull` 用「项目游标前进」判断要不要拉增量，而全局变量 `project_id=0` **不推进项目游标** → 管理员只改全局变量时永远拉不到。协议 `syncapi.State` 增加 `global_cursor`（share **v0.15.1**），服务端 `/sync/state` 回报全局变量最新变更 id，客户端在「`cursor` 或 `global_cursor` 任一前进」时拉一次增量，基线存 `.sync.json`。
- **单测**：`server/internal/service/sync_globalvar_test.go`（增量 + 全量都附带）、`sync_state_test.go`（GlobalCursor 前进且不推进项目游标）；`client/internal/syncengine/globalvar_test.go`（落 globals.yml 且不混进环境）、`globalcursor_test.go`（只动全局游标也能应用）；`client/internal/app/env_global_test.go`（参与解析、环境覆盖全局、禁用不生效）。
- **端到端**：`.tmp/sync-test/verify_r253.py` —— 服务端建 scope=3 变量 → 客户端 `globals.yml` 出现且不混进环境文件（PASS）。
- **遗留**：客户端变量面板未展示全局变量（UI 待排期，不影响取值）。
- **状态**：✅ 已完成

### R3　接口发布状态 / 版本 / 废弃时间不同步　【高】　✅ 已完成（客户端 UI 待排期）

- **现象**：`model.Api` 有 `status`（1 草稿 / 2 已发布 / 3 已废弃）、`version`、`deprecated_at`，但同步 `Payload` 无对应键，客户端模型也没有。
- **影响**：Web 标「已废弃 / 草稿」的接口，客户端仍当正常接口；两端对「能不能调」的判断割裂。
- **落地**：
  - 协议：`Payload` 新增 `api_status` / `version` / `deprecated_at` 三键（键名带 `api_` 前缀，与 example 的 `status`（HTTP 状态码）区分）。
  - 服务端：`apiSyncPayload` 下发三键；`applyUpsert` 按「键存在才覆盖」落库 —— **客户端回推不含这三键，服务端状态不会被同步抹掉**。
  - 客户端：`collection.Request` 增三字段并落请求文件 `meta` 段（`share.FileMeta` 增同名字段，空值不落盘，老集合文件字节不变）；`syncengine/lifecycle.go` 负责落地，缺键不改。
- **单测**：`server/internal/service/sync_lifecycle_test.go`（下发带状态 / 客户端回推不抹掉 / 带状态键可改）；`client/internal/syncengine/lifecycle_test.go`（落盘保留 + 缺键不清空）。
- **遗留**：客户端界面未展示「已废弃」徽标（UI 待排期；数据已不丢）。
- **状态**：✅ 已完成

### R4　集合级公共参数（defaults）不同步　【中】　⬜ 待排期

- **现象**：集合级公共 header / auth 只存在客户端 manifest（`collection/defaults.go`），服务端无对应实体。
- **影响**：队友同步下来的请求缺公共头/认证，跑集合结果与本地不同。
- **方案**：新增同步实体（项目级单例，uid 固定）并建表 + 迁移，改动涉及协议、服务端模型/迁移、客户端 manifest 读写与变量合并顺序。**本轮未做**：需要新增表与迁移，风险高于收益，排在 R6/R7 之后。
- **状态**：⬜ 待排期

### R5　文档同层顺序（seq）不同步　【中】　✅ 已完成

- **现象**：客户端 `DocEntry.Seq`（frontmatter 同层排序权重）不在 `Payload` 里（`Seq` 键被 example 占用），服务端 `Doc.Priority` 也不下发。
- **影响**：同一目录下的文档在两端顺序不一致。
- **落地**：`Payload` 新增独立键 `doc_seq`；服务端 `docSyncPayload` 下发 `priority`、`applyUpsert` 按缺键不改落库；客户端 `collectDocOps` 上推 `seq`、`applyDoc` 落地（缺键不清空）。
- **补强（端到端联调发现）**：服务端 `SortNodes`（Web 拖拽排序/移动）只改 `priority` / `group_id`，**不写 `change_log`** —— 客户端增量永远拉不到，单独拖拽排序后两端顺序一直不一致；拖拽「移动接口/文档到别的分组」同样不同步。现 `sortGroup` / api / doc 三分支落库后 `recordChange`（分组改为返回对象以便取 `ext_uid`）。
- **单测**：`server/internal/service/sync_lifecycle_test.go`（`TestSyncDocSeqRoundTrip`）、`sort_change_test.go`（`TestSortNodesRecordsChange` / `TestSortNodesApiMoveRecordsChange`）、`client/internal/syncengine/doc_seq_test.go`。
- **端到端**：`POST /api/sort {kind:doc, priority:7}` → 客户端 `docs/项目说明.md` 的 `seq: 7`（PASS）。
- **状态**：✅ 已完成

### R6　导出 / 导入格式不对称　【中】　⬜ 待排期

- **现象**：客户端只能导出 Markdown / HTML / `.apidocgo.json` 集合包；服务端能导出 OpenAPI / Postman。反之服务端不能导入 `.apidocgo.json` 集合包（只支持 OpenAPI / Postman / Bruno）。
- **影响**：客户端 ⇄ Web 之间搬运集合需绕道 OpenAPI，中间信息（脚本、断言、gRPC、响应文档）丢失。
- **方案**：服务端增加 `.apidocgo.json` 导入；客户端增加 OpenAPI 导出（可参考服务端 `service/extra.go`）。
- **状态**：⬜ 待排期

### R7　客户端无法只读打开分享链接　【中】　⬜ 待排期

- **现象**：服务端 `/share/:token` 免登录只读；客户端只能绑定项目后同步查看，无「打开分享链接只读浏览」入口。
- **影响**：分享是唯一面向非成员的分发通道，客户端作为主要消费端打不开。
- **方案**：客户端新增「只读打开分享链接」——拉 `/share/:token` 的只读数据，在内存虚拟集合中浏览（不落盘、不参与同步）。
- **状态**：⬜ 待排期

### R8　Web 侧展示字段不同步　【低】　⛔ 判定不做

- **现象**：接口 `group_id_second`（二级分组）、`develop_language`、`source`、文档 `like_count` / `view_count` / `is_top` 不在同步载荷内。
- **判定**：`group_id_second` 在服务端无独立「二级分组」实体，Web 端仅回填、无选择入口 → 不补；点赞 / 浏览量是 Web 侧计数 → 不补；`source`（导入来源）与 `develop_language` 属同类展示元数据，暂不补。
- **状态**：⛔ 判定不做
