# 客户端与服务端同步实现现状

> 记录时间：2026-10-10
> 范围：基于当前代码梳理客户端（api-doc-go-client）与服务端（api-doc-go）同步的实际实现方式，以及多客户端使用者场景的行为。

## 一、总体模型：文件即真相源 + 服务端变更流水

同步建立在两个不对称的真相源之上：

- **客户端**：本地集合是纯文本 YAML 文件（Bruno 风格），文件即真相源，离线可用；
- **服务端**：SQLite/PostgreSQL 中的项目数据，外加一张只存"指针"的 `change_log` 变更流水表。

核心代码：

- 客户端：`internal/syncengine/`（`engine.go`、`client.go`）
- 服务端：`server/internal/{service,handler,repository,model}/sync.go`
- 设计依据：服务端仓库 `doc/客户端与同步架构设计.md` §4

## 二、绑定方式（类似 git 的 origin）

同步是**每个本地集合自己的属性**，不是服务端项目的属性。绑定信息存在集合目录下的 `.sync.json`：

```json
{
  "linked": true,
  "serverUrl": "https://...",
  "projectId": 10,
  "mode": "auto",
  "cursor": 4201
}
```

- `serverUrl / projectId / mode` 可以随集合文件共享给同事；
- **PAT（个人访问令牌）只存内存**（`internal/app/multicoll.go` 的 `setSyncToken/syncTokenOf`），绝不落盘、绝不进集合文件——同事 clone 后只需填自己的 PAT；
- 服务端地址有安全校验：非回环地址禁止明文 http，防止令牌明文上网（`syncengine/client.go` 的 `ValidateServerURL`）。

三种同步模式：

| 模式 | 行为 |
|---|---|
| `auto`（默认） | 定时双向：自动 pull + push |
| `manual` | 本地改动自动 push，pull 只能手动点 |
| `mirror` | 只拉不推，本地是服务端的只读镜像 |
| 未关联 | 纯单机，无任何服务端交互 |

## 三、一轮同步的流程（顺序固定：先 pull 后 push）

- 入口：`App.RunSync`；前端弹窗：`frontend/src/components/SyncDialog.vue`。
- `auto` 模式有定时器（默认 120 秒一轮，且只对当前活动集合生效，`StartAutoSync`）。

引擎 `Engine.RunOne()` 步骤：

1. `GET /api/sync/state` 探测服务端最新游标；
2. 游标比本地新 → `GET /api/sync/changes?since=<游标>` 分页增量拉（每页 500）；
3. 若返回 `gap:true`（本地游标太老、流水已被清理）→ 改走 `GET /api/sync/snapshot` 全量重对齐；首次绑定（cursor=0）也走 snapshot；
4. 应用条目时**两阶段排序**：先 group 后 api/doc，保证父目录先就位；
5. 收集本地 hash 变化的 dirty 节点 + 待推送删除，`POST /api/sync/push` 提交。

单轮最多拉取 200 页；游标不推进时停止，避免无限循环。

## 四、服务端机制

- **`change_log` 流水表**：`{id, project_id, entity_type, ext_uid, op, actor, device}`，项目级游标就是它的自增 id；
- 每个实体带 `ext_uid`（客户端生成的 UUID，离线改名/移动不丢身份）和 `last_change_id`（条目当前版本）；
- **Web 端写操作同样记流水**（device 标记为 `"web"`，见 `service/content.go` 的 `recordChange`），所以在网页上做的修改也会流向所有客户端；
- **push 幂等**：`sync_op` 表记录已处理的 `op_id`，网络重试不会重复落库；
- **鉴权**：`AuthOrPAT` 中间件同时接受 JWT 和 PAT；
- **写开关**：项目 `client_write_enabled=false` 时所有 push 返回 `rejected.readonly`，负责人可一键禁止客户端写入。

## 五、冲突处理：LWW + 冲突副本

- **判定**：push 时 `op.base_rev` 与服务端该条目的 `last_change_id` 不一致 → 返回 `conflict` 并附带服务端当前版本。比较的是版本号而非时间戳，避免时钟权威问题；
- **处理**：服务端版本落回原文件，本地版本另存到 `.conflicts/*.yml`，该条不 MarkSynced、下次仍 dirty；UI 提供「以本地覆盖 / 以远端覆盖 / 保留副本」三选一；
- pull 时若本地恰好有未推送改动，会先把本地版本存进 `.conflicts/` 再让远端覆盖（`saveLocalIfDirty`）；
- 字段级三方合并是后续增强，v1 不做。

## 六、多个客户端使用者的场景

所有关联同一项目的客户端**共享一条 change_log 流，各自维护自己的 cursor**。流水里的 `actor`（用户 id）和 `device`（设备名）记录每一次变更是谁、在哪台设备做的。

| 场景 | 行为 |
|---|---|
| A 在设备 1 改接口 | push 成功 → 服务端写流水；B 下一轮 pull 按 uid 找到本地文件直接覆盖，B 本地干净时无打扰提示 |
| A、B **同时编辑同一条** | 后 push 的一方 base_rev 已过期 → `conflict`，不会静默覆盖对方改动，走冲突副本流程 |
| A、B **各自新建同名请求** | uid 不同 → 服务端产生两条记录，**不猜、不合并**，UI 提示可能重复 |
| A 删除接口 | 软删 + tombstone 流水；B pull 后文件移入 `.trash/`；离线的 B 即使又改了它再 push 也会被 tombstone 挡住，**不会"复活"已删条目** |
| A 删除分组 | 只软删组本身、子接口保留；B 收到后移除 `folder.yml` 但保留目录和子文件，子项呈"未分组"（与 Web 行为一致） |
| Web 回收站还原 | is_deleted=0 + upsert 流水，各端自动恢复文件 |
| 某客户端**长期离线** | cursor 超出流水保留窗口 → `gap` → 自动 snapshot 全量重建对齐 |
| 只读成员/无 update 权限 | push 返回 `rejected.forbidden`，被视为正常路径而非错误；mirror 模式则天然只拉不推 |
| 多人共享集合配置 | `.sync.json` 可提交到 git，每人只填自己的 PAT 即完成绑定 |

## 七、当前实现与设计文档的差距（待办）

1. **sync push 路径目前未见项目成员/权限位校验**：设计 §4.2 要求"全部挂现有鉴权 + 项目权限位"，但现在的 `SyncPush` 只验证身份（JWT/PAT 有效）和 `client_write_enabled` 开关，没有像普通写路径那样调 `ensureProjectPermission` 检查调用者是否为该项目成员、是否有对应权限位。当前代码下任何持有效令牌的用户理论上可向任意 project_id 推送——属于实现欠账，建议补上。
2. **实际同步范围目前只有 group / api / doc 三类**：设计中列出的 variable、variable_env、field_mapping 及 secret 加密同步（§4.7）尚未接入客户端同步引擎。
3. **文档（doc）条目 push 未做 dirty 过滤**：目前每轮会把所有文档全量推送，数据量大时可优化为只推内容 hash 变化的条目。
