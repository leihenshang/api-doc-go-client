# 客户端与服务端同步实现现状

> 记录时间：2026-10-15（依据当前代码核对，非设计规划）
> 范围：客户端（api-doc-go-client）↔ 服务端（api-doc-go）↔ Web 的同步实际实现，以及多客户端场景行为、各字段在 Web 端的展示情况。

## 一、总体模型：文件即真相源 + 服务端变更流水

同步建立在两个不对称的真相源之上：

- **客户端**：本地集合是纯文本 YAML（Bruno 风格），文件即真相源，离线可用；
- **服务端**：SQLite/PostgreSQL 中的项目数据，外加一张只存"指针"的 `change_log` 变更流水表。

核心代码：客户端 `internal/syncengine/{engine,client}.go` + `internal/collection/{syncrows,sync_extra_fields}.go`；服务端 `server/internal/{service,handler,repository,model}/sync.go`；设计依据 `doc/客户端与同步架构设计.md` §4。

## 二、绑定方式（类似 git 的 origin）

同步是**每个本地集合自己的属性**，绑定信息（含 PAT）存集合目录下 `.sync.json`（`{linked, serverUrl, projectId, mode, cursor, token}`，权限 0600）。

- **PAT 持久化在本地、但不进集合的版本库**：`.sync.json` 由集合自动维护的 `.gitignore` 排除（`internal/collection/collection.go` 的 `gitignoreContent` 含 `.sync.json`），令牌只落本机磁盘、**不随集合文件提交给同事**；关闭集合 / 关闭客户端后重开仍读得到，免重填。令牌解析顺序为「显式参数 → 会话内存 → `.sync.json` 持久化值」（`app.go` 的 `RunSync`，回退到 `syncTokenOf` / `syncengine.LoadBind`），同一服务端只改模式/项目时无需重输；
- **要分享已绑定的集合需先解绑**：`.sync.json` 是本地个人配置，`UnbindSync` 会清空它（含 PAT）；同事拿到集合目录后各自填自己的 PAT 重新绑定；
- 服务端地址安全校验：非回环地址禁止明文 http（`syncengine/client.go` 的 `ValidateServerURL`）。

| 模式 | 行为 |
|---|---|
| `auto`（默认） | 定时双向：自动 pull + push（默认 120 秒一轮，仅对当前活动集合，`StartAutoSync`） |
| `manual` | 本地改动自动 push，pull 只能手动点 |
| `mirror` | 只拉不推，本地是服务端的只读镜像 |
| 未关联 | 纯单机，无任何服务端交互 |

## 三、一轮同步的流程（顺序固定：先 pull 后 push）

入口 `App.RunSync`，前端弹窗 `SyncDialog.vue`。引擎 `Engine.RunOne()`：

1. `GET /api/sync/state` 探测服务端最新游标；
2. 游标比本地新 → `GET /api/sync/changes?since=<游标>` 分页增量拉（每页 500，单轮上限 200 页；游标不推进即停，避免死循环）；
3. 返回 `gap:true`（游标太老、流水已清理）或首次绑定（cursor=0）→ 走 `GET /api/sync/snapshot` 全量重对齐；
4. 应用条目**两阶段排序**：group → doc/api → example（示例依赖请求文件，排最后），保证父级先就位；
5. 收集本地 hash 变化的 dirty 节点 + 待推送删除（tombstone），`POST /api/sync/push` 提交。

## 四、服务端机制

- **`change_log` 流水表**：`{id, project_id, entity_type, ext_uid, op, actor, device}`，项目级游标即自增 id；实体类型 `group / api / doc / example` 四类都记流水；
- 每个实体带 `ext_uid`（客户端生成 UUID，离线改名/移动不丢身份）和 `last_change_id`（当前版本）；
- **Web 端写操作同样记流水**（device 标 `"web"`，见 `service/content.go` 的 `recordChange`），网页改动也会流向所有客户端；
- **push 幂等**：`sync_op` 表记录已处理 `op_id`，网络重试不重复落库；
- **鉴权**：`AuthOrPAT` 中间件同时接受 JWT 和 PAT；
- **写开关**：项目 `client_write_enabled=false` 时所有 push 返回 `rejected.readonly`。

## 五、冲突处理：LWW + 冲突副本

- **判定**：push 时 `op.base_rev` 与服务端该条目 `last_change_id` 不一致 → 返回 `conflict` 并附服务端当前版本（比版本号而非时间戳，避开时钟问题）；
- **处理**：服务端版本落回原文件，本地版本另存 `.conflicts/*.yml`，该条不 MarkSynced、下次仍 dirty；UI 提供「以本地覆盖 / 以远端覆盖 / 保留副本」三选一；
- pull 时本地若有未推送改动，先存进 `.conflicts/` 再让远端覆盖（`saveLocalIfDirty`）；
- 字段级三方合并是后续增强，v1 不做。

## 六、多个客户端使用者的场景

所有关联同一项目的客户端**共享一条 change_log 流，各自维护 cursor**；流水的 `actor`（用户 id）和 `device`（设备名）记录每次变更来源。

| 场景 | 行为 |
|---|---|
| A 改接口 | push 成功写流水；B 下轮 pull 按 uid 覆盖本地文件，B 本地干净时无打扰提示 |
| A、B 同时编辑同一条 | 后 push 方 base_rev 过期 → `conflict`，不静默覆盖，走冲突副本 |
| A、B 各自新建同名请求 | uid 不同 → 两条记录，**不猜、不合并**，UI 提示可能重复 |
| A 删除接口 | 软删 + tombstone 流水；B pull 后文件入 `.trash/`；离线的 B 再改再 push 也被 tombstone 挡住，不"复活" |
| A 删除分组 | 只软删组本身、子接口保留；B 移除 `folder.yml` 但保留子文件，子项呈"未分组" |
| Web 回收站还原 | is_deleted=0 + upsert 流水，各端自动恢复文件 |
| 某客户端长期离线 | cursor 超出流水保留窗口 → `gap` → 自动 snapshot 全量重建 |
| 只读/无 update 权限 | push 返回 `rejected.forbidden`（正常路径非错误）；mirror 天然只拉不推 |

## 七、同步实体与字段范围（核对结论）

**实体类型**：当前两端都同步 **group / api / doc / example** 四类。
`example` 是独立实体（服务端表 `api_return_sample`：`name / status / content_type / seq / api_id`），即"多响应示例"，客户端与服务端均已接入。

**接口（api）携带的字段**：客户端 `SyncExtra` 已把「可填字段」全部下发；服务端现已为扩展字段建列，并在 `applyApiExtra` / `apiSyncPayload` 双向往返，Web 详情新增只读段展示。关键结论（2026-10-15 落地）：

- **已全链路（下发 → 落库 → 展示）**：请求体（`bodyType/body/bodyForm`）、认证（`auth`）、请求设置（`settings`：超时/跟随重定向/最大重定向/跳过 SSL/URL 编码）、脚本（`script/vars/asserts`）、单样例响应内容类型（`retContentType`）。服务端以**原始 JSON/文本列**存储、原样回传；Web 查看态新增「请求体 / 认证 / 请求设置 / 脚本」四段 + 返回参数内容类型徽标。
  - 落库口径沿用 `headers/params`：整份覆盖、空串清空、缺键不动，旧客户端 / 旧服务端互相兼容；三态布尔（followRedirects/insecureSsl）由客户端编码为 `-1/0/1` 存进 JSON，服务端不解释。
  - Web 编辑保存会把这些列原样回传（整条覆盖式更新），不会误清同步来的值。
- **`bodyDescs`（请求体字段备注）**：随共享包 `Body.Descs` 发版（v0.8.1）已全链路接入——客户端桌面端提供「请求体 原文 / 表格」切换与备注编辑（`BodyFieldsTable.vue` 写回 `body.descs`，`e2e` B5 验证落盘），`SyncExtra`/`ApplySyncExtra` 携带该键，服务端 `http_request_body_descs` 列存储并原样回传，Web「请求体」段展示 path→备注表。至此 api 携带的扩展字段**全部端到端且有真实录入入口**。

> 即"同步字段补全与响应类型改造方案"的服务端建列 + Web 展示 + `bodyDescs`（依赖共享包 `Body.Descs`）均已落地；共享包 v0.8.1 已发版，客户端 / 服务端依赖同步升级。
