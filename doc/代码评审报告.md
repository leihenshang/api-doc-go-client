### 1.3 总体结论

**架构层面：合格，且有多处值得肯定的设计。** 分层清晰、依赖方向克制（客户端用接口注入破除 `app ↔ mcp` 环依赖）、安全默认值到位（MCP 与 Mock 服务默认只绑回环）、同步协议的端点与字段两端一致。

**安全层面：2 个 P0 级越权漏洞，优先于一切其他事项。** 服务端写接口普遍做了项目级权限校验，**读接口普遍没做**——任意登录用户改一个 `project_id` 即可读取他人项目的全部分组、接口、文档与环境变量明文，并可枚举全库分享令牌。这不是理论风险：同一文件内 `DeleteGroup`（有 `PermDelete` 校验）与 `ListGroups`（无校验）相隔仅 5 行。

**同步正确性：4 个 P0，且集中在同一条链路。** 服务端 `applyUpsert` 反序列化失败后用零值覆盖存量数据——**客户端 `engine.go:350` 是完全相同的缺陷**，即推送与拉取两个方向都会静默损坏数据；`SetLastChange` 缺变量/环境分支导致变量类修订号永为 0；变量与环境的 Web 写路径完全不写 `change_log`，使"双向同步"对变量实际是单向的。

**测试：核心链路几乎裸奔。** 客户端 `internal/syncengine` 覆盖率 **6.9%**，服务端 `handler` / `repository` / `password` 均为 **0%**——**最复杂的代码恰好是最没有测试保护的代码**。

**工程层面：两个仓库的门禁脚本都不带 `-race`、不带覆盖率阈值**，因此以上问题全部不会被 CI 拦截。

**同时必须指出**：两个项目的 `gofmt` 与 `go vet` 均零告警，客户端在并发安全、MCP 鉴权与监听地址上的安全默认值设计得相当扎实（详见 2.1）。这是一份有底子的代码库，问题集中在"同步链路的正确性"与"服务端的鉴权覆盖面"两处，而非整体工程质量失控。

### 2.2 职责边界与模块划分

**判定：边界总体清晰，但共享库的"收权"做了半截。**

`api-doc-go-share` 已承载 `codegen / collection / mock / openapi / postman / varx`（12 个文件，客户端 11 处、服务端 7 处引用），覆盖了代码生成、变量解析、导入导出格式这类"纯规则"——这个切分是对的。

但**两类本该共享的东西没有下沉**：

1. **同步协议契约**：两端各自定义了一套完全对应的结构体，字段名与 JSON tag 手工保持一致。
   - 服务端：`internal/service/sync.go:21-123`（`SyncStateResp` / `SyncItem` / `SyncOpIn` / `SyncPushReq` / `SyncOpOut` / `SyncPushResp` / `MetaResp` / `SyncPayload`）
   - 客户端：`internal/syncengine/client.go:128-190`（同名结构的镜像）
   - `share` 中**没有 sync 包**，尽管两端都已依赖 share。
2. **业务实体模型**：服务端 `internal/model/{api,doc,group,variable}.go` 与客户端 `internal/collection/types.go`（`Request` / `ResponseDoc` / `Env` / `CollectionInfo`）各自定义；`share/collection/types.go` 只有 `RequestSettings` / `KV` / `Body` / `Auth` / `Node` 这 5 个偏传输层的类型，核心实体仍留在两端。

**后果**：契约与模型靠"人工同步"维护，一旦漂移只能在运行时暴露；而 `share` 是第三方仓库（见 2.3），改一次要走发版，团队很可能因此选择继续复制——这会持续恶化。

### 2.3 依赖与版本锚定（重点隐患）

```
api-doc-go/server/go.mod      → require github.com/leihenshang/api-doc-go-share v0.10.0   (无 replace)
api-doc-go-client/go.mod      → require github.com/leihenshang/api-doc-go-share v0.10.0   (无 replace)
api-doc-go-share/go.mod       → module github.com/leihenshang/api-doc-go-share, go 1.25
```

三个目录是三个独立 git 仓库。**两边都没有 `replace` 指令**，意味着：

- 本地 `api-doc-go-share/` 工作副本的改动**对两个工程完全不可见**，必须推远端 + 打 tag + 改 go.mod 才能消费；
- 三仓无法原子联动：一次跨端的契约变更要发三次版，中间态必然是坏的；
- `share` 声明 `go 1.25`，两端声明 `go 1.26`，版本基线不一致。

### P0 — 必须立即修复

#### P0-1 服务端读接口普遍缺失项目级鉴权，任意登录用户可越权读取他人项目（IDOR）

- **位置**：`api-doc-go/server/internal/service/content.go:86, 151, 156, 346, 357`；`internal/service/extra.go:47, 85, 203`；`internal/service/token.go:66`；`internal/service/variable.go:513`
- **证据**（同一文件内 5 行之隔的显式不一致）：
  ```go
  // content.go:91  DeleteGroup —— 有鉴权
  func (s *Service) DeleteGroup(ctx context.Context, userID uint64, typ int8, id uint64) error {
      g, err := s.repo.GetGroup(ctx, id)
      ...
      if err := s.ensureProjectPermission(ctx, userID, typ, g.ProjectID, model.PermDelete); err != nil {
          return err
      }
  // content.go:86  ListGroups —— 无鉴权，且签名里根本没有 userID / typ
  func (s *Service) ListGroups(ctx context.Context, projectID uint64, typ int8) ([]model.Group, error) {
      return s.repo.ListGroups(ctx, projectID, typ)
  }
  ```

#### P0-3 同步 upsert 反序列化失败仍用零值覆盖存量数据，可静默清空服务端内容

- **位置**：`api-doc-go/server/internal/service/sync.go:621-624`（`applyUpsert`）
- **证据**：
  ```go

      _ = json.Unmarshal(op.Payload, &p)   // 失败被完全吞掉

  // 随后无条件执行：e.Title = p.Title / e.ApiName = p.Name / e.URL = p.URL ...
  ```


- **修复方向**：两端同时改为 `if err := json.Unmarshal(...); err != nil { return / rejected + Reason:"bad_payload" }`，并补一条"非法 payload 不改变本地/远端状态"的回归测试。

### P1 — 高优先级隐患

#### P1-1 同步批量写入无事务，中途失败留下部分提交

- **位置**：`api-doc-go/server/internal/service/sync.go:537-551`；全仓范围
- **证据**：`for _, op := range req.Ops { ... res := s.applyOp(...); _ = s.repo.SaveSyncOp(...) }` 顺序执行。全仓 grep `Transaction|Begin(|Commit(|Rollback` **零命中**——整个服务端没有任何事务边界。
- **影响**：一批 20 个操作中第 15 个失败，前 14 个已落库且已推进 `change log`，客户端拿到的是"部分成功"。对于依赖修订号做冲突检测的同步协议，这会产生不可逆的状态漂移。
- **补充证据（并发侧）**：`service/sync.go:247` 的冲突检测持有 Postgres `SELECT ... FOR UPDATE` 悲观锁，但 `service/sync.go:502-507`（`SyncState`）不持锁；`service/sync.go:270-296`（快照路径）不校验 `expectOldest`、不持锁。即**同一份数据，push 路径加锁、state 与 snapshot 路径不加锁**——并发拉取时可能读到被另一个事务锁住/未提交的行，锁策略本身不自洽。
- **修复方向**：将 `SyncPush` 的单批操作包进 `db.Transaction`，失败整体回滚并返回批次级错误；若确实要保留"逐条结果"语义，至少保证「业务写入 + `AppendChange` + `SaveSyncOp`」三项在同一事务内。同时统一 `state` / `snapshot` 与 `push` 的锁策略。

#### P1-2 幂等记录写入失败被吞，导致操作被重复应用

- **位置**：`api-doc-go/server/internal/service/sync.go:547`
- **证据**：`_ = s.repo.SaveSyncOp(ctx, &model.SyncOp{...})`
- **影响**：`SaveSyncOp` 是幂等的唯一凭据（`:540` 通过 `GetSyncOp(op.OpID)` 判重）。写入失败时客户端收到 `ok`，重试后服务端查不到历史记录 → **同一操作被再执行一次**。叠加 P1-3 会把"重复执行"放大成"重复创建实体"。
- **修复方向**：失败即返回该条为 `rejected`（`Reason: "idempotency_write_failed"`），让客户端明确重放。

#### P1-3 查询错误与"记录不存在"不可区分，误判为不存在 → 创建重复实体

- **位置**：`api-doc-go/server/internal/service/sync.go` 多处
- **证据**：
  ```go
  e, _ := s.repo.FindGroupByExtUID(ctx, req.ProjectID, op.UID)   // :632
  if e == nil { e = &model.Group{...} }                          // 进入"新建"分支
  ```
  同类模式见 `FindApiByExtUID`、`:601` `FindVariableByExtUID`、`:337` `LatestChangeID`。
- **影响**：一次瞬时 DB 错误（连接抖动、超时）会让 `e == nil` 成立，代码走进"新建"分支，**生成一条重复实体**。这是把错误路径伪装成正常路径的典型形态。
- **修复方向**：`e, err := ...; if err != nil && !errors.Is(err, repository.ErrNotFound) { return rejected }`。注意 `service/content.go:518` 已有 `var _ = repository.ErrNotFound`，说明该哨兵错误已定义但未在此处正确使用。

#### P1-4 八处变更日志写入传 nil context 且错误被吞，变更会静默丢失

- **位置**：`api-doc-go/server/internal/service/content.go:29`；`sync.go:660, 696, 731, 766, 793, 835, 909`
- **证据**：`cid, err := s.repo.AppendChange(nil, ...)` → `if err == nil { _ = s.repo.SetLastChange(nil, ...) }`
- **影响**：
  - 传 `nil` 破坏 context 传播：超时与取消无法下达到 DB 层，也丢失链路追踪；
  - `AppendChange` 失败时 `cid` 为 0，该实体的变更**不会进入 change log，客户端永远拉不到**；
  - `SetLastChange` 失败时实体 `LastChangeID` 不更新，下次推送的 `base_rev` 与服务端不匹配 → 冲突检测失效。

#### P1-5 集合 YAML 采用非原子直写，崩溃即损坏且无备份

- **位置**：`api-doc-go-client/internal/collection/collection.go:432, 1243, 1492, 1759, 1842, 1947`；`doc.go:205, 227`；`example.go:132, 304`；`export.go:70`；`proto.go:73`
- **证据**：全部为 `os.WriteFile(path, data, 0o644)`，全仓未见「写临时文件 + `os.Rename` 原子替换」模式（`os.Rename` 仅出现在移动/回收站场景：`collection.go:1558/1599`、`trash.go:78/256`）。
- **影响**：项目定位是"文件即真相源"。写入过程中进程崩溃、断电、磁盘满，YAML 会被截断成半份——用户整个集合不可恢复。"文件即真相源"的前提是写入必须原子。

#### P1-6 门禁不含 `-race` 与覆盖率阈值，上述缺陷无法被拦截

#### P1-9 `UserProject` 缺联合唯一索引，`AddMember` 用「先删后插」而非 upsert，并发下产生重复成员行

#### P1-10 客户端 `App` 门面在锁外替换集合指针，与前端并发调用构成竞态

- **位置**：`api-doc-go-client/internal/app/app.go:319-400`

- **影响**：Wails 绑定方法被前端并发调用是常态（集合树刷新 + 后台同步 + MCP 工具调用）。锁外换指针会导致读到一个正在被关闭的集合句柄。
- **修复方向**：把 `app.go:319-400` 的三处也纳入 `a.mu`；`collOrder` 改用显式顺序切片而非每次 `mapOrder` 重建（`app.go:47`）。建议对 `internal/app` 跑一次 `go test -race` 复现。

#### P1-11 Mock 服务与限流器存在资源泄漏

- **位置**：`api-doc-go-client/internal/mocksrv/mock.go:47-55`；`api-doc-go/server/internal/middleware/ratelimit.go`
- **证据**：`mock.go` 中 `go func() { _ = s.srv.Serve(ln) }()` 启动后，`Stop()` 只 `Close()` listener，未等待该 goroutine 退出；限流器用 `map[string]*counter` 全局累计，无 TTL 清理。
- **影响**：前者在频繁切换集合启停 Mock 时累积孤儿 goroutine；后者随不同 IP 增长而**无界占用内存**，且可被构造大量伪造 `X-Forwarded-For` 触发 OOM。
- **修复方向**：`Stop()` 增加 `done chan struct{}` 并等待；限流器改为带过期时间的分片 LRU，`MaxEntries` 上限 10000，并对代理头做可信校验。

#### P1-12 PAT 明文落库且比较非恒定时间

- **位置**：`api-doc-go/server/internal/service/token.go:69, 160`
- **证据**：PAT 明文存储；校验时用 `strings.Split` 拆串后逐段比较（`:160`）。
- **影响**：数据库泄露即等价于全量凭证泄露；非恒定时间比较理论上可被计时侧信道利用（本地场景风险较低，但修复成本极低）。
- **修复方向**：落库只存 HMAC-SHA256 摘要；比较改用 `crypto/subtle.ConstantTimeCompare`。

#### P1-13 密钥派生混入 `time.Now()`，跨进程不可复现（待复核）

- **位置**：`api-doc-go-client/internal/secrets/svc.go:24-60`
- **证据**：派生参数包含 `time.Now().Unix()`，且 PW 与 KEY 两条路径的 AAD 不一致。
- **说明**：**此项由静态审查得出，本轮未实测复现，标注为待复核**。若成立，则密文换机器/换时钟后无法解密——对"集合文件即真相源"的客户端是灾难性的（用户换电脑后集合里的加密变量全部失效）。
- **修复方向**：派生只依赖稳定输入（passphrase + salt + 固定 domain separator）；补一条"跨进程解密一致性"测试。

#### P1-14 事件总线只有单个订阅槽位，MCP 审计与 devserver SSE 会互相顶掉（潜在 P0）

- **位置**：`api-doc-go-client/internal/app/app.go:1517`（`nextEventID`）；`internal/mcp/service.go:174`（`a.SubscribeEvents`）；`internal/app/mcp_audit.go:35`（`aud.Subscribe`）
- **证据**：`App` 只有 `events *eventSub` 单槽位（对比 `mcp_audit.go` 的 `map[uint64]...` 多订阅模型）。两处调用各自：
  ```go
  id := a.Subscribe(...)          // 都断言 emptyID == 0 —— 说明作者已知只有一个槽位
  ```
  `mcp/service.go:174` 与 `mcp_audit.go:35` **都**调用订阅，后绑定者覆盖先绑定者的槽位。
- **影响**：当前只在"启动顺序恰好串行且只绑一个"时正常工作。**一旦 MCP 服务与审计器同时启用，或绑定顺序调整，其中一个的事件流会被永久静默丢弃**——devserver 模式下前端 SSE 断流，或 MCP 工具调用审计日志静默丢失（审计是安全能力，丢失等于失效）。
- **严重度说明**：目前尚未触发（属潜伏缺陷），故定为 P1；但它是"改动一行即变成 P0"的那类问题，建议与 P0 同批修复。
- **修复方向**：把 `App.events` 改为 `map[uint64]*eventSub` 多订阅模型（与 `mcpaudit` 现有一致），`nextEventID` 用 `a.mu` 保护的单调计数器。

#### P1-15 `nextEventID` 无锁生成，并发下产生重复 ID 覆盖订阅槽位

- **位置**：`api-doc-go-client/internal/app/app.go:1517`
- **证据**：`id := uint64(len(a.events))` 类实现，读取与写入分离且未持 `a.mu`。
- **影响**：两个前端/后台调用并发订阅时拿到相同 id，后者覆盖前者——与 P1-14 同源，两者应一并修。
- **修复方向**：改为 `a.mu` 保护的自增序号。

#### P1-16 `internal/mcp` 违规挂载 Wails 绑定方法，且前端有 16 处调用

- **位置**：`api-doc-go-client/internal/mcp/service.go`（`GetMCPStatus` / `StartMCPServer` / `StopMCPServer` / `UpdateMCPConfig`）；调用方 `frontend/src/lib/ipc.ts:106-155`
- **证据**：`internal/mcp` 包内出现 Wails 绑定风格注释，自述"疑似调试残留"；但前端 `ipc.ts` 有 16 处对应调用。
- **影响**：双重风险——(a) 职责越界：MCP 实现包直接暴露给前端，绕过 `internal/app` 门面，与"门面是唯一出口"的约定冲突；(b) 若实为残留，前端 16 处调用会在重构时集体失效。
- **修复方向**：先确认是否为残留。若为残留 → 收敛到 `internal/app` 门面并同步改 `ipc.ts`；若为正式能力 → 在 AGENTS.md 中明确"MCP 设置允许直连"并给出理由，消除歧义。

#### P1-17 `syncengine` 的口令缓存是进程级 `sync.Once`，切换集合后无法重试

- **位置**：`api-doc-go-client/internal/syncengine/engine.go:29`
- **证据**：`var passphraseOnce sync.Once`（包级）。
- **影响**：用户输错一次同步口令后，`sync.Once` 已消费，**整个进程生命周期内再也不会重新询问**——切换集合、切换项目都救不回来，只能重启应用。这是明确的功能性缺陷。
- **修复方向**：改为按 (root, projectID) 维度的 `map + mutex` 缓存，或每次失败重置。

#### P1-18 用文本正则改写 YAML，会误伤字符串与注释内容

- **位置**：`api-doc-go-client/internal/syncengine/engine.go:1127`（`PatchYAMLString`）
- **证据**：以文本/正则方式定位并替换 YAML 字段。
- **影响**：YAML 是结构化格式，正则改写遇到「值里含同名字段」「注释里出现 key」「多行块标量」时会写坏文件。客户端定位是"文件即真相源"，写坏即数据损坏。
- **修复方向**：改为 yaml.Node 解析后按路径定位节点再序列化。

#### P1-19 变量占位符语法两端不一致，共享 `varx` 库并未统一语义

- **位置**：`api-doc-go-share/varx/varx.go`；`api-doc-go/server/internal/service/variable.go:290-350`；`api-doc-go-client/internal/varx/varx.go:118`
- **证据**：共享库 `varx` 与服务端均按 `{{name}}` 解析，而客户端 `internal/varx/varx.go:118` 使用 `{{$name}}` 语法（带 `$` 前缀）。
- **影响**：客户端已依赖 `share/varx` 处理部分场景，却又自带一套语法不同的同名实现。结果是：同一段带变量的请求体，在客户端能正确替换、推到服务端后替换失败（或反之），而 UI 上不会报错，只会发出一个带着 `{{...}}` 原文的脏请求。
- **修复方向**：二选一并全量统一——建议统一到 `{{name}}`（服务端与 share 已是这个），客户端删掉自带实现、全部改调 `share/varx`；并在 share 中加一条"语法一致性"的跨端契约测试。
