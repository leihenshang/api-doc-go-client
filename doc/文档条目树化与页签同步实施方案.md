## 2. 目标、非目标与关键约定

### 2.1 目标

1. **文档与请求同级、无隶属关系**：`.md` 叶子可出现在任意分组目录，与 `.yml` 请求文件同目录混排，支持拖拽（文档拖入/拖出分组，复用 `useTreeDnd` + `canDrop`）。
2. **点击叶子开文档页签**：由 `DocEditor`（编辑 / 分栏 / 预览）承载，具备与请求一致的能力：脏点、手动 / 自动保存（`ExpectHash` 冲突检测）、关闭确认、重启恢复、撤销重做、mirror 只读。
3. **树与页签按根归属**：文档属于所在根的本层目录；切根换页签组（机制已存在）。
4. **删除闭环**：行内删除走 `App.DeleteDoc`（进 `.trash/`，B5 语义）；新增 / 修改 / 删除三类变更均同步到服务端（J11，含**目录归属 = 服务端分组**）。

### 2.2 非目标（范围裁剪，避免阶段膨胀）

- 文档**不进** SQLite 索引（正文 / URL 检索不覆盖文档，另立项）。
- 重命名**只改 frontmatter `name`**，不改文件名（与 B7 分组语义一致）。
- `README.md` 不视为文档条目。
- 文档**无子级**（不能拖到文档下）。
- 服务端**核心链路不改动**（同步/doc CRUD 均已就绪），仅按 §7 补「文档分组树」接口。
- Web 需改造：见 §7（文档按分组树展示、按分组新建/移动）。
- `App.SyncDocAssets(token)` 仍无调用方（见《代码问题分析》G-04）：本方案不接线，阶段三统一决策（接线 / 标注预留 / 移除）。

### 2.3 关键约定（全文只写一次）

- 存量兼容：`docs/` 保留为**默认新建位置**（根级）；旧集合 `docs/*.md` 继续按现有路径识别并挂根，**无数据迁移**。
- 同层排序：`folder` 在前，`request`/`doc` 按 `seq`（frontmatter 可选键，`docFront.Extra` 已 round-trip）再按名称。
- 旧持久化数据（无 `kind` 字段）反序列化时补默认 `'request'`，**向后兼容、无迁移脚本**。

## 3. 数据契约（改动前先定）

### 3.1 文件层

| 项 | 约定 |
|---|---|
| 识别 | `scanExtAllowed`：`.md` 放开到任意目录，排除文件名 `README.md` |
| 挂载 | doc 叶子由「强制挂根」改为按 `Dir(Path)` 挂载（`ensureDir(dir)`，与请求同路径语义） |
| 创建 | `CreateDoc(name, uid, folder)`：空 folder → `docs/`；非空 → `<groupdir>/<sanitize(name)>.md` |
| 移动 | `MoveDoc(uid, destFolder)`：仿 `MoveRequest`——`resolveFolderForMove` 拒后代 + 改 Path + `os.Rename`；**uid 与文件名主干不变** |
| 重命名 | `RenameDoc(uid, name)`：只改 frontmatter `name` |
| 门面 | 新增 `App.MoveDoc`/`App.RenameDoc`；`App.CreateDoc` 增加 folder 参（缺省空串，旧调用不破） |

### 3.2 前端类型

```ts
// types.ts
export type TreeNodeType = 'folder' | 'request' | 'doc'

// stores/tabs.ts —— 最小侵入扩展
interface Tab {
  kind: 'request' | 'doc'   // 旧持久化 JSON 无此字段 → 反序列化补 'request'
  request: RequestDoc | null // doc 页签为 null；所有读取方用 kind 守卫
  doc?: { uid: string; path: string; name: string; content: string; icon: string }
}
```

- **必须逐个排查 `Tab.request` 的读取方**：`TabBar` 徽标、`RequestEditor` 挂载、`send`、H7 快照、撤销重做栈、`lib/quit.ts` 退出守卫。
- 显隐：doc 页签时响应面板整体隐藏（`v-if="tab.kind === 'request'"`），编辑区满幅；发送 / 取消 / 代码生成入口同步隐藏；mirror 只读沿用 `isReadOnly`。

### 3.3 同步（J11）

| 方向 | 约定 |
|---|---|
| push 归属 | `collectDocOps` 的 payload 补 `GroupUID`（= `d.Path` 父目录对应的 folder uid；根级 / `docs/` 下为空串 → 服务端未分组） |

## 7. 阶段四：Web 端文档展示（api-doc-go/web）

> 目标：文档在 Web 端**按分组树展示**（与客户端文档叶子同级混排的模型对齐），并支持按分组新建 / 移动文档。

### 7.1 必须先定：文档归位策略（阻塞 7.2 全部任务）

客户端树化后文档与请求**共用目录**，其目录对应服务端 `group` 记录；而 Web 文档树当前只消费 `type=3` 的文档分组。三选一：

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **A（推荐）** | Web 文档树数据源由「`type=3` 分组列表」改为「项目下**含文档的分组**（不分 type）+ 未分组」；文档与请求可共用同一分组 | 服务端新增/改造一个分组树接口；Web 换数据源 | 与客户端同级模型一致，**无数据迁移**，改动最小 |
| B | 客户端文档目录在服务端落成 `type=3` 文档分组（与同名接口分组并存两条记录） | 服务端分组翻倍，与客户端「同目录混排」语义不一致 | 不推荐 |
| C | 统一分组体系：接口与文档共用一棵分组树 | 需数据迁移 + 接口树改造 | 改动最大，可作为远期目标 |

| 4.9 | 分享页文档展示保持 | `web/src/views/ShareView.vue` | 仅验收，不改动 |

### 7.3 验收

- 接口层：文档分组树返回含文档的分组（含客户端同步上来、挂在请求分组下的文档）与未分组文档。
- Web 手工/e2e：① 客户端在请求分组内建文档并同步 → Web 文档页树中该分组下可见该文档；② Web 选中分组新建文档 → 落在该分组而非未分组；③ Web 改文档分组 → 回推客户端（下一次 pull 落位到对应目录）；④ 删除闭环：客户端删文档 → Web 侧同步消失（依赖阶段二 J11）。
- 门禁：服务端 `GOWORK=off go test ./internal/service/`；Web `vue-tsc --noEmit` + `npm run i18n:check`（需先 `npm install`，当前 `web/node_modules` 未安装）。

### 7.4 依赖与排序

**阶段二（J11：push `GroupUID` + 删除闭环）→ 7.1 决策 → 4.1（服务端）→ 4.2~4.7（Web）→ 4.8（i18n/testid）→ 验收。**
阶段四可与阶段三并行开发，但必须**分别提交、分别验证**（跨仓库）。

## 8. 风险与回滚

| 风险 | 缓解 | 回滚 |
|---|---|---|
| 扫描白名单放开后，外部笔记 md 被当文档，改变既有集合观感 | 排除 `README.md`；白名单改动单列提交（1.1），`scanExtAllowed` 集中一处易收紧 | 还原 1.1 即回到「仅 `docs/`」；文件不会被删，仅识别行为变化 |
| 拖动后重推整篇 doc（hash 因换路径而变）产生冗余 upsert | 服务端按 `ext_uid` 幂等覆盖，仅多一条 `change_log` | 无需处理；若噪声大可后续按 (uid, content) 去重 |
| `Tab` 类型放宽引发请求路径回归 | 所有 `request` 读取点用 `kind` 守卫 + 阶段一全量 e2e | 阶段一为独立提交序列，`git revert` 即回到弹窗形态（`DocsDialog` 到阶段三才删，天然保留回退面） |
| 旧 localStorage 页签数据无 `kind` | 反序列化默认 `'request'`，无迁移脚本 | 兼容读取即可 |
| doc 删除同步误删本地文件 | 走 `.trash`（可恢复）；tombstone 仅对「推送记录在册」的 uid 生效 | 阶段二独立提交；服务端删除本就有冲突副本机制 |
| 文档误拖到非法位置（文档无子级） | `canDrop` 目标只允许 folder / 根；`MoveDoc` 层再校验 | 行为收缩在前端 lib 层，随时可收紧 |
| **Web 文档树只认 `type=3` 分组**，客户端把文档放在请求目录下时 Web 看不到（§7.1） | 先定归位策略再动工；推荐方案 A（数据源改为「含文档的分组」） | 未决策前不实施 4.x；数据源切换为单个接口调用点，可单独还原 |
| 阶段四跨仓改动（服务端 + Web）互相耦合 | 服务端 4.1 与 Web 4.2~4.7 **分别提交、分别验证**（§7.4） | 两仓各自 revert 即可，不影响客户端阶段一~三 |
| Web 侧 `web/node_modules` 未安装，改动无法类型检查 | 阶段四动工前先 `npm install`（node v22.16.0 可用：`/usr/lib/uos-ai-agent/node/bin`） | 门禁缺失时只提交不验证，需标注并补验 |

## 9. i18n 与 testid 清单（阶段一 / 阶段四同步交付）

- **i18n**：`zh-CN.ts` / `en-US.ts` 的 key 必须一一对应，改完跑 `npm run i18n:check`（门禁项）。建议在 `tree` 段补文档行相关文案、在 `docs` 段补页签与保存相关文案。
